# dynamicState 개선 전략과 로드맵

- **작성일**: 2026-11-13
- **기준**: 브랜치 `feat/visual-incident-report` (커밋 `bba6cf7`). main(`8c4ac43`)을 기준으로 한 외부 구현 분석을 코드와
  대조해 평가한 결과이다.
- **상태**: 진행 중. 6.1의 결정이 내려졌고 0·1·2·5단계의 대부분이 통합 브랜치 `stage1/integ`에 구현됐다. 진행 현황은 8장.
- **관련 문서**: `docs/EXTENDING_DIAGNOSIS.md` (진단 추가 방법), `docs/HEALTHY_VERDICT.md`, `docs/consistency_model.md`,
  `benchmarks/diagnosis_accuracy/README.md`. 2026-11-09의 `FUNCTIONAL_GAP_ANALYSIS_AND_DEVELOPMENT_ROADMAP.md`는
  이전 시점의 기록이다.

## 1. 요약

진단에 필요한 구성요소는 대부분 있다. 부족한 것은 세 가지다.

1. **판정 경로의 정직성.** 가설 검증 일부가 문장 속 단어 검색에 의존하고, 가설 모델이 둘로 나뉘어 있으며, 내장 검사 22개 중
   7개는 무정지 모드에서 결론을 낼 수 없다.
2. **원인 특정.** 결함의 종류는 찾지만(21/21), 원인 줄을 맞히는 비율은 낮다(8/21). 이 중 상당수는 무정지 관측으로는 볼 수
   없는 호출 지점이다.
3. **재현성.** 호스트 부하에 따라 같은 대상의 판정이 달라지는 경우가 있다.

전략의 원칙은 하나다. **판정에 실제로 영향을 주는 경로를 먼저 정직하게 만들고, 그다음에 정교하게 만든다.** 가설 선택을
수식으로 최적화하는 일은, 증거와 가설이 구조화된 뒤에 한다.

## 2. 현재 기준선

2026-11-13, AArch64 / glibc 2.39, 부하가 낮은 상태에서 측정. 두 증상 모드(정답 증상, generic)의 결과가 같다.

| 지표 | main `8c4ac43` | 현재 브랜치 |
|---|---|---|
| 채점 대상 결함 검출 | 11/11 | 21/21 |
| 원인 이름 완전 일치 / 부분 일치 | 8 / 2 | 16 / 4 |
| 원인 위치(file:line) 일치 | 4 | 8 |
| CONFIRMED / PROBABLE | 5 / 6 | 11 / 10 |
| 정상 대조군 통과 | 7/8 | 7/8 (`ok_sawtooth`는 계속 "판단 불가") |
| 오탐 / 놓친 결함(HEALTHY 판정) | 0 / 0 | 0 / 0 |
| 기본(항상 실행) 검사 수 | 8 | 14 |
| 채점 제외 대상 | 2 (`long_stall`) | 6 (`long_stall` 2, 단편화 2, 락 경합 2) |

브랜치에서 추가된 진단: 고아 락, 자기 교착, 락 경합(성능 저하), 스레드 누수, malloc 밖 메모리 증가, 힙 단편화(성능 저하),
이중 해제. 보고서에는 발견별 그림과 검사 체크리스트가 생겼고, 진단 하나를 파일 하나로 추가하는 구조
(`recipe_plugins/` + `report_registry.py`)가 갖춰졌다.

검증 상태: 전체 테스트는 `bba6cf7`에서 통과했다(2,534개, 실패 0, 건너뜀 1, AArch64). 그 직전 실행에서는 실패가 2건
있었다. 1건은 수정했고, 1건은 간헐 실패로 이번 실행에서는 나오지 않았으나 원인은 찾지 못했다(4.1 참조). x86-64는 CI에서만
확인 가능하고 아직 푸시하지 않았다.

## 3. 외부 분석의 타당성 평가

### 3.1 코드로 확인된 지적

| 분석의 주장 | 확인 결과 | 근거 위치 |
|---|---|---|
| 계획 점수가 사실상 상수 | 사실. 정보 획득량 0.80, 실행 가능성 0.90, 비용 0.95 고정. 진단 가치는 `verification_procedure` 문자열 길이로만 갈린다 | `expert_diagnostic_engine.py` `score_and_build_step` |
| 정보 획득량이 가설 구별력을 재지 않음 | 사실. 적용되는 미해결 가설 수만 센다(`20 + 15 × 개수`). 가설별 예상 결과가 없다 | `observation_selector.py` |
| 가설 모델이 둘로 분리 | 사실. 최종 판정은 검사 결과와 `ExpertHypothesis`만 받는다. 경쟁 가설 비교 결과는 판정에 들어가지 않는다 | `_step_narrow`, `DiagnosticVerdictAggregator.aggregate` 호출부 |
| 검증이 문자열 포함 여부에 의존 | 사실. `"growth"`/`"leak"`, `"stable"`/`"plateau"`, `"deadlock"`/`"blocked"` 등을 증거를 문자열로 바꿔 검색한다 | `_execute_verification_for_hypothesis` |
| MCP 보고서 경로가 둘 | 사실. `investigation_id` 유무에 따라 생성 경로와 데이터 구조가 다르다 | `scripts/mcp_server.py` `runtime_export_incident_report` |
| 벤치마크 수치 | 사실 (main 기준 11/11, 8, 4, 5/6) | `benchmarks/diagnosis_accuracy/results/` |

### 3.2 현재 브랜치 기준으로 낡았거나 일부만 맞는 지적

- **문제별 설명이 3종뿐**: 일부 해소. HTML에는 교착·오버플로·누수·해제 후 사용·스레드 이상 그림이 있고 새 진단은 전용 문장과
  그림을 갖는다. 남은 것은 오버플로와 해제 후 사용의 쉬운 말 요약 문장(아직 일반 문구)이다.
- **HTML 구성**: 요약, 발견별 그림, 체크리스트는 있다. 경쟁 가설, 시간순 타임라인, 증거 계보는 접힌 A–I 상세에만 있다.
- **이중 읽기 일관성**: 전무하지 않다. 힙 손상, 해제 후 사용, 이중 해제, 락 검사는 재읽기로 안정성을 확인한다. 구조체 필드
  불변식 쪽은 이 평가에서 확인하지 못했다. 지적의 방향은 옳다. 경합 중 읽기 시점 때문에 자기 교착 오판이 실제로 나왔고
  이번에 고쳤다.

### 3.3 동의하지 않거나 보완이 필요한 지점

- **"레시피 22개, 양호"는 과대평가다.** 이중 해제(이번에 대체됨), 추적 기반 해제 후 사용, 의심스러운 할당 패턴, 객체 수명
  이상, 예상 밖 변수 변화, 상태 전이 위반, 공유 상태 불일치는 판정 규칙이 읽는 값을 어떤 수집기도 채우지 않는다.
- **"추가보다 통합이 우선"은 절반만 맞다.** 진단을 추가하는 과정에서 기존의 놓친 결함 2건이 드러났다. 자기 교착과 tcache
  이중 해제가 HEALTHY로 판정되고 있었다. 적용 범위의 공백도 실제 위험이다.
- **정보 획득량 수식의 우선순위는 낮다.** 값싼 검사는 대부분 기본으로 항상 실행되므로, 무엇을 고르느냐가 결과에 미치는
  영향이 작다. 선택이 의미 있는 곳은 비싼 후속 검사(힙 조사, 추적)뿐이다.
- **위치 일치율에는 구조적 한계가 있다.** 위치를 못 맞히는 13건은 누수 3, 오버플로 2, 해제 후 사용 2, 이중 해제 2, 스레드
  누수 2, 매핑 증가 2이다. 모두 원인 줄이 할당·해제·쓰기·스레드 생성의 호출 지점이고, 한 시점의 메모리를 읽는 방식으로는 그
  호출을 볼 수 없다.
- **LLM 표준화는 엔진 밖에 둔다.** MCP 호출자가 이미 LLM이다. 엔진은 구조화된 증상 필드를 선택 입력으로 받으면 되고, 엔진
  안에 LLM 의존을 넣을 이유가 없다.

### 3.4 분석이 놓친 것

- **분류 오류가 이미 발생한다.** "memory usage of this process keeps growing"이 메모리 누수가 아니라 상태 불일치로 분류된다.
- **부하에 따른 판정 흔들림.** 부하가 높으면 정상 프로세스가 "판단 불가"로, 일부 결함(`spin_yield`)이 HEALTHY로 나온다.
- **기본 검사 증가의 비용.** 8개에서 14개로 늘면서 진단 시간이 늘었고(매핑 증가 검사만 약 0.9초), 고정 단계 상한이 계획을
  잘라 "판단 불가"로 끝나는 문제가 실제로 났다(수정됨: 상한 기본값을 계획 길이에서 계산).
- **미검증 환경.** 새 진단의 x86-64와 원격 대상 경로.

## 4. 로드맵

각 단계는 앞 단계의 완료 조건을 전제로 한다. 기간은 적지 않았다. 범위가 확정되면 단계별로 산정한다.

### 4.1 0단계: 안정화

목표: 현재 브랜치를 믿을 수 있는 기준선으로 만든다.

| 작업 | 완료 조건 |
|---|---|
| 푸시, x86-64 CI (AArch64 전체 테스트는 `bba6cf7`에서 통과) | 두 아키텍처에서 통과 |
| 간헐 실패 원인 규명: `test_ordinary_contention_stays_healthy`가 긴 실행에서 2회 "판단 불가". 단독·조합·16회 반복에서는 재현되지 않음 | 원인을 특정하고 수정하거나, 부하 조건을 명시한 재현 절차 확보 |
| 부하 시 판정 흔들림 조사 (`spin_yield`, `ok_contention`) | 같은 대상 20회 반복 판정 일치율을 벤치마크 지표로 추가하고 수치 기록 |
| `ok_sawtooth` 정상 판정 | 통과하거나, 통과할 수 없는 이유를 범위 한계로 문서화 |
| 진단당 시간 기록 | 벤치마크 결과에 대상별 진단 시간과 기본 검사별 시간 포함 |
| 새 진단의 원격 대상 경로 시험 | 원격 테스트 추가 또는 미지원으로 명시 |

### 4.2 1단계: 판정 경로 정리

목표: 판정에 쓰이는 모든 입력이 구조화된 값이다. 죽은 코드가 없다.

| 작업 | 완료 조건 |
|---|---|
| 타입이 있는 증거 규격 정의 (종류, 측정값, 관측 범위, 완결성, 일관성 확인 여부) | 검증 규칙이 증거의 필드만 읽는다 |
| `_execute_verification_for_hypothesis`의 문자열 검색 제거 | 판정 경로에 `in str(e)` 형태의 조건 0건. 문구를 바꿔도 판정이 같다는 테스트 |
| 가설 모델 통합: `CompetingHypothesis`와 `ExpertHypothesis`를 하나로. 지지·반박 조건과 필요한 증거를 가설이 직접 가진다 | 최종 판정과 보고서 F절이 같은 가설 객체를 읽는다 |
| 결론을 낼 수 없는 레시피 6개 처리: 값을 채울 수집기를 만들거나, "이 모드에서 미지원"으로 계획에서 제외 | 실행되면 항상 "판단 불가"인 검사 0개. 기본 증상 계획에서 `예상 밖 변수 변화` 잡음 제거 |
| 정상 판정은 "증거가 있음"이 아니라 "검증 조건이 충분한 범위에서 완료됨"일 때만 | 범위 미달 시 CONTRADICTED가 아닌 "판단 불가"가 되는 테스트 |

### 4.3 2단계: 증상 해석

목표: 같은 문제를 다르게 표현해도 같은 조사 계획이 나온다.

| 작업 | 완료 조건 |
|---|---|
| 구조화된 증상 입력(선택): 증상 종류, 빈도, 지속 시간, 영향 영역, 관련 객체 | `diagnose`, MCP, 웹 API가 같은 필드를 받는다. 자유 문장만 줘도 지금처럼 동작한다 |
| 바꿔 쓴 문장 묶음으로 분류 회귀 테스트 (한국어·영어) | 묶음 안의 문장들이 같은 계획을 만든다. 현재의 오분류 사례 포함 |
| 분류 신뢰도가 낮을 때의 동작 명시 | 낮은 신뢰도에서는 넓은 계획으로 가고, 보고서에 그 사실을 적는다 |

### 4.4 3단계: 원인 특정

목표: "무엇이, 어느 객체가, 어디에서"에 답한다. 관측한 것과 후보를 구분한다.

| 작업 | 완료 조건 |
|---|---|
| 원인 이름 미일치 보강 (`busy_wait` 이름 일치 0/2, 누수 1건) | 이름 완전 일치율 향상, 수치 기록 |
| 정적 위치 후보: DWARF에서 해당 변수에 쓰거나 해제하는 호출 지점을 찾아 "후보(관측 아님)"로 제시 | 위치 일치율을 "관측"과 "후보"로 나눠 집계 |
| 객체 관계 모델(범위를 좁힌 인과 그래프): 발견 → 메모리 객체 → 소유 변수·컨테이너 → 스레드. 기존 누수 소유자 경로와 포인터 참조 지도를 한 모델로 | 누수·해제 후 사용·이중 해제·오버플로가 같은 모델을 쓰고 보고서에 그림으로 나온다 |
| C++ 컨테이너 해독기를 기본 진단 경로에 연결 (`std::string`, `vector`, `shared_ptr`) | 크기 > 용량 같은 불변식 위반이 진단된다 |
| 선택적 추적 모드 (6장의 결정에 따름) | 할당·해제·쓰기 호출 지점을 관측으로 보고 |

### 4.5 4단계: 적응형 조사

목표: 비싼 검사만 똑똑하게 고른다.

| 작업 | 완료 조건 |
|---|---|
| 레시피별 실측 비용 기록 (이미 수집 중인 영향 수치 활용) | 계획 점수의 비용이 상수가 아닌 실측값 |
| 레시피 메타데이터: 무엇을 증명하는가, 직접 증거인가, 적용 조건 | 진단 가치가 문자열 길이가 아닌 선언된 값 |
| 비싼 후속 검사에 한해 가설별 예상 결과표 작성, 그 표로 다음 검사 선택 | 선택 로그에 "이 결과면 H1 지지, 저 결과면 H2 지지"가 남는다 |
| 종료 조건: 추가 검사의 기대 이득이 비용을 정당화하지 못하면 멈춤 | 예산 내 결론 도달률과 진단당 시간으로 효과 측정 |

### 4.6 5단계: 보고서 통합

목표: 하나의 표준 모델에서 모든 출력이 나온다.

| 작업 | 완료 조건 |
|---|---|
| `DiagnosticReport`를 표준으로 MCP 경로 단일화 | `runtime_export_incident_report`의 생성 경로 1개 |
| HTML에 경쟁 가설 비교, 시간순 타임라인, 증거 계보 추가 (스크립트 없이) | 세 가지가 접힌 상세가 아닌 본문에 있다 |
| 오버플로·해제 후 사용의 쉬운 말 요약 문장 | 일반 문구 대신 전용 문장 |

## 5. 순서의 근거

- **1단계가 4단계보다 먼저다.** 가설과 증거가 구조화돼야 예상 결과표를 쓸 수 있다. 지금 수식부터 넣으면 문자열 위에 수식을
  얹게 된다.
- **0단계가 모든 것보다 먼저다.** 판정이 부하에 따라 달라지면 이후 단계의 개선을 수치로 확인할 수 없다.
- **진단 추가는 멈추지 않는다.** 확장 구조가 있으므로 새 진단은 다른 단계와 병행할 수 있다. 다만 기본 검사로 넣을 때는
  진단 시간과 정상 판정 차단 여부를 0단계의 지표로 확인한다.

## 6. 결정이 필요한 사항

1. **추적 모드의 범위.** 위치 일치율을 실질적으로 올리려면 eBPF/uprobe 추적이 필요하다. 이는 "무정지·읽기 전용" 기본 원칙
   밖이다. 선택 기능으로 둘지, 범위에서 뺄지에 따라 3단계 설계가 달라진다. 빼는 경우 위치는 "정적 후보"까지만 제공한다.
2. **기본 검사의 시간 예산.** 기본 검사가 늘수록 모든 진단이 느려진다. 진단당 허용 시간을 정하고, 넘는 검사는 증상이 있을
   때만 실행하도록 할지 결정이 필요하다.
3. **성능 저하 진단의 채점.** 단편화와 락 경합은 결함이 아니어서 채점에서 빠져 있다. DEGRADED를 정답으로 채점하는 방식을
   벤치마크에 추가할지 결정이 필요하다.

### 6.1 결정 (2026-11-13)

1. **추적 모드는 선택 기능으로 둔다.** 기본은 무정지·읽기 전용을 유지한다. 위치는 "정적 후보"와 "추적 관측"을 구분해
   보고한다.
2. **기본 검사에 진단당 시간 예산을 적용한다.** 예산을 넘는 검사는 증상이 있을 때만 실행한다. 예산 값은 실측을 근거로
   정한다(통합 브랜치 `13fb0d7`, 조용한 호스트: 정상 대상의 기본 검사 합계 약 2.7초, 그중 매핑 증가 0.9초, FD 누수
   0.8초, 프로세스 메모리 증가 0.7초).
3. **DEGRADED는 벤치마크 채점에서 제외한다.** 단편화와 락 경합 대상은 지금처럼 참고 정보로만 출력한다.
