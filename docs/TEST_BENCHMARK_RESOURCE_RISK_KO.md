# 시험·벤치마크 실행 자원 및 SSH 안정성 위험 분석

**분석 일자:** 2026-11-15  
**범위:** 저장소에 있는 시험/벤치마크 실행기와 이들이 띄우는 대상 프로세스. 실제 장애 호스트의 메트릭, 커널 로그, SSH 로그는 제공되지 않아 본 문서는 코드 기반 위험 분석이며 SSH 끊김의 직접 원인을 확정하지 않는다.

## 요약

코드상 가장 큰 즉시 위험은 [load_repro.py](../benchmarks/diagnosis_accuracy/load_repro.py)다. `--load K`가 K개의 우선순위 조정 없는(`nice 0`) 무한 busy loop 프로세스를 띄우며 CPU 수 대비 입력을 제한하지 않는다. 프로세스 트리 정리와 최대 수명은 구현돼 있지만 실행 중 CPU 포화는 의도된 동작이다. SSH가 같은 호스트에서 동작하거나 그 호스트의 네트워크/VM 자원을 공유한다면 응답 지연 또는 연결 실패를 유발할 수 있다.

일반 시험에서는 메모리 증가/CPU 스핀/교착 상태를 흉내 내는 결함 대상이 다수 실행된다. 다만 장기 실행 대상은 대부분 `fixture_process` 런처를 통해 실행되며 부모 종료, RSS 상한, 최대 수명, 트리 정리 방어를 갖춘다. 이 보호는 픽스처별 RSS 한도일 뿐 전체 작업의 메모리/CPU 할당량을 제한하지 않는다. 테스트 실행기와 빌드 도구에도 호스트 전체 자원 격리는 없다.

따라서 “비정상 앱”은 시험이 의도적으로 실행하는 결함 시뮬레이션일 가능성이 높지만, SSH 장애 원인으로 단정할 수는 없다. 특히 `load_repro --load`의 과도한 부하, 전체 테스트와 별도 벤치마크의 동시 실행, 시험 대상 장비 자체의 메모리 부족을 먼저 구분해야 한다.

## SSH 장애와 코드의 관계

저장소에서 `sshd`를 종료하거나 SSH 서비스 설정을 바꾸는 시험 코드는 이번 조사에서 확인되지 않았다. 원격 진단 및 QEMU 시험은 SSH 클라이언트를 사용하지만, 조사한 코드에서는 대상 OS의 SSH 데몬을 직접 조작하지 않는다. 그러므로 SSH가 끊겼다는 현상은 다음의 간접 경로가 더 그럴듯하다.

1. 호스트 CPU 포화로 `sshd`, 네트워크 인터럽트 처리, 터미널 세션이 스케줄링을 제때 받지 못한다.
2. 메모리 압박/OOM으로 커널이 SSH 또는 시험 프로세스를 종료하거나, 시스템이 응답 불능이 된다.
3. 원격 보드에서 시험 대상이 보드 CPU/메모리를 소비한다. QEMU 매트릭스는 게스트에 1 vCPU를 주지만, 실보드 경로는 실제 장비 용량을 사용한다.
4. 클라이언트 연결 타임아웃/네트워크 장애 등 저장소 외부 원인.

원인 확정에는 장애 시각의 `journalctl -k`/OOM 기록, `sshd` 로그, 메모리·swap·load·프로세스 수 추세, 실행 명령과 동시 작업 기록이 필요하다. 현재 코드만으로 특정 시험 실행과 SSH 재접속 실패의 인과관계를 증명할 수 없다.

## 권장 완화 설계

### P0 — 안전한 실행 습관

- SSH로 접속한 중요 장비에서는 `load_repro.py`와 `collection_impact_benchmark.py`의 로컬 부하 시나리오를 실행하지 않는다. 필요하면 별도 실험 장비/VM에서 수행한다.
- `load_repro.py`를 써야 한다면 우선 `--load 0` 또는 코어 수보다 작은 값으로 시작하고, 한 번에 하나의 부하형 벤치마크만 실행한다. 현재 스크립트는 큰 `--load`도 허용하므로 입력값을 신뢰하지 않는다.
- 테스트 베이스라인은 제한된 장비에서 `BASELINE_JOBS=1`로 실행한다. 빌드/전체 테스트/벤치마크를 동시에 실행하지 않는다.
- 중요 보드에서는 실행 전 원격 관리 경로(콘솔/전원제어)와 복구 방법을 확보하고, SSH 연결만을 유일한 제어 수단으로 두지 않는다.

### P1 — 실행기 기본값을 fail-safe하게 변경

1. **적용됨:** `load_repro.py`는 가용 CPU 절반 기준 `--load` 상한(최대 2, 절대 16), nice +10, `--n` 1..100 제한, worker 수명 상한을 적용한다. 기본 상한 초과는 `--allow-heavy-load`로만 가능하다.
2. **적용됨:** `run_test_baseline.sh`는 기본 병렬도를 `min(2, 가용 CPU)`로 제한하고, 잘못된 병렬도·timeout 및 CPU 수를 초과하는 병렬 실행을 거부한다. CI의 `BASELINE_JOBS=2`는 4-vCPU runner에서 계속 유효하다.
3. **미적용 권장 사항:** 테스트 실행을 cgroup v2/systemd scope 또는 컨테이너로 묶어 **작업 단위 총 메모리 및 CPU quota**를 적용한다. cgroup을 사용할 수 없는 환경에서는 명시적으로 격리 미적용을 알리고, 동시 실행도를 1로 낮춘다. 픽스처별 RSS watchdog은 계속 보조 안전망으로 둔다.
4. 상위 runner에 전체 timeout과 종료 시 자식 프로세스 그룹 정리를 추가한다. 각 unittest 파일의 timeout만으로는 전체 실행 시간을 제한하지 못한다.
5. 상태 출력에 실행 PID/PGID, 선택된 CPU 수, 자원 제한값, 종료 결과를 기록한다. 중단/timeout 시 잔류 프로세스 검사를 수행한다.

### P2 — 측정과 운영 절차

- 전용 시험 장비/VM에서만 부하 benchmark를 허용하고, 실제 운영 보드에서는 CPU·RSS·swap·load average·OOM 카운터를 시험 전후에 기록한다.
- SSH 세션은 `tmux`/`screen` 등으로 보존하되, 이것은 세션 복구 수단일 뿐 호스트 자원 고갈을 막는 보호책으로 간주하지 않는다.
- 장애 보고에는 실행 커맨드, commit, 시작/종료 시각, 부하 파라미터, `dmesg`/커널 OOM 로그, `journalctl -u ssh` 로그와 자원 지표를 포함한다.

## 우선순위 표

| 순위 | 변경 | 기대 효과 |
|---|---|---|
| 1 | `load_repro --load` 상한 + 낮은 기본 부하 + nice/affinity | 가장 명확한 CPU 포화 경로를 직접 축소 |
| 2 | 시험·벤치마크 작업 단위 cgroup 메모리/CPU 제한 | 여러 픽스처의 자원 합산으로 인한 호스트 고갈 방지 |
| 3 | 테스트 runner 병렬도 및 전체 timeout 보수화 | 저사양/원격 호스트에서 자원 급증 및 장시간 잔류 감소 |
| 4 | 원격 보드 실행 전용 격리 및 관측 절차 | 실제 SSH 장애의 원인 판별 및 복구성 향상 |

## 결론

가능성 있는 코드가 확인됐다. 특히 `load_repro.py --load`는 CPU를 의도적으로 전부 점유할 수 있어 SSH 응답 저하와 연결되기 쉬운 위험 경로다. 일반 시험의 비정상 대상도 자원을 사용하지만, 픽스처 관리 장치가 있어 통제 의도가 확인된다. 다만 fixture별 RSS 한도와 정리 기능은 CPU 부하나 전체 작업의 자원 합계를 제한하지 않는다. 우선 부하 재현기 입력 제한과 시험 작업 단위 자원 격리를 적용하고, 실제 SSH 장애 로그로 인과관계를 확인하는 것이 적절하다.
