# 속성 기반 테스트 규칙 (Property-Based Testing Rules)

## 개요

이 속성 기반 테스트 (PBT) 규칙은 해당하는 AI-DLC phase 전반에 적용되는 공통 제약이다. 식별 가능한 속성을 가진 코드를 속성 기반 기법으로 테스트하도록 보장하며, 기존의 예시 기반 테스트를 대체하지 않고 보완한다.

속성 기반 테스트는 모든 유효한 입력에서 성립해야 하는 불변 조건을 정의한 뒤, 프레임워크로 무작위 입력을 생성해 반례를 찾는다. 실패를 찾으면 프레임워크가 입력을 최소 재현 사례로 축소 (shrink) 한다. 이 방식은 예시 기반 테스트가 흔히 놓치는 경계 사례와 미묘한 버그를 찾아낸다.

**강제 (Enforcement)**: 적용 대상인 각 stage 에서 모델은 사용자에게 stage 완료 메시지를 제시하기 전에 이 규칙의 준수 여부를 **반드시** 검증한다.

### 차단성 PBT 발견 사항 처리 (Blocking PBT Finding Behavior)

**차단성 PBT 발견 사항 (blocking PBT finding)** 의 의미:
1. 해당 발견 사항은 stage 완료 메시지의 "PBT 발견 사항 (PBT Findings)" 섹션에 PBT 규칙 ID 및 설명과 함께 **반드시** 나열한다
2. 모든 차단성 발견 사항이 해결될 때까지 stage 는 "다음 Stage 로 진행 (Continue to Next Stage)" 선택지를 **절대** 제시하지 않는다 (MUST NOT)
3. 모델은 무엇을 바꿔야 하는지 명확한 설명과 함께 "변경 요청 (Request Changes)" 선택지만 **반드시** 제시한다
4. 해당 발견 사항은 PBT 규칙 ID, 설명, stage 맥락과 함께 `aidlc-docs/audit.md` 에 **반드시** 기록한다

PBT 규칙이 현재 프로젝트나 unit 에 해당하지 않으면 (예: 상태를 가진 구성요소가 없는데 PBT-06), 준수 요약에 **N/A** 로 표시한다 — 이는 차단성 발견 사항이 아니다.

### 기본 강제 수준 (Default Enforcement)

이 문서의 모든 규칙은 기본적으로 **차단성 (blocking)** 이다. 어떤 규칙의 검증 기준이라도 충족되지 않으면 차단성 PBT 발견 사항이며 — 위에서 정의한 차단성 발견 사항 처리를 따른다.

### 부분 강제 모드 (Partial Enforcement Mode)

사용자가 opt-in 에서 **부분 (Partial)** 강제를 선택했다면, PBT-02, PBT-03, PBT-07, PBT-08, PBT-09 규칙만 강제한다. 나머지 규칙은 모두 권고 (비차단) 로 취급한다. 강제 모드는 `aidlc-docs/aidlc-state.md` 의 `## Extension Configuration` 아래에 기록한다.

### 검증 기준 형식 (Verification Criteria Format)

이 문서의 검증 항목은 준수 여부 점검을 설명하는 일반 글머리 기호 목록이다. 각 항목은 검토 시 준수 또는 미준수로 평가한다.

## Rule PBT-01: 설계 단계의 속성 식별 (Property Identification During Design)

**규칙**: 비즈니스 로직, 데이터 변환, 알고리즘 연산을 포함한 모든 unit 은 Functional Design stage 에서 테스트 가능한 속성을 **반드시** 분석한다. 분석에서는 다음 속성 분류 중 어떤 것이 해당하는지 **반드시** 식별한다:

| 분류 | 설명 | 예 |
|---|---|---|
| 왕복 (Round-trip) | 연산과 그 역연산을 이어 적용하면 원래 값이 나온다 | serialize → deserialize = identity |
| 불변 조건 (Invariant) | 변환이 측정 가능한 어떤 특성을 보존한다 | 정렬은 컬렉션 크기와 원소를 보존 |
| 멱등성 (Idempotence) | 연산을 두 번 적용한 결과가 한 번 적용한 결과와 같다 | dedup(dedup(list)) = dedup(list) |
| 교환 법칙 (Commutativity) | 연산 순서가 달라도 같은 결과가 나온다 | add(a, b) = add(b, a) |
| 오라클 (Oracle) | 참조 구현이나 단순화한 모델로 결과를 검증할 수 있다 | 최적화 알고리즘 vs 무차별 대입 |
| 귀납 (Induction) | 작은 입력에서 증명된 속성이 큰 입력으로 확장된다 | 재귀 구조, 분할 정복 |
| 쉬운 검증 (Easy verification) | 결과를 계산하기는 어렵지만 확인하기는 쉽다 | 미로 풀이 결과는 따라 걸어 보며 검증 가능 |

식별한 속성은 해당 unit 의 functional design 산출물에 **반드시** 문서화하고, 코드 생성 단계로 PBT 테스트 요구사항으로 이어서 넘긴다.

**검증**:
- functional design 산출물에 구성요소별로 식별한 속성을 나열한 "테스트 가능한 속성 (Testable Properties)" 섹션이 있음
- 식별한 각 속성이 위 분류 중 하나를 참조함
- 식별 가능한 속성이 없는 구성요소는 간단한 근거와 함께 "PBT 속성 없음 (No PBT properties identified)" 으로 명시함
- 코드 생성 계획 수립 시 속성 목록을 참조함

## Rule PBT-02: 왕복 속성 (Round-Trip Properties)

**규칙**: 논리적 역연산이 있는 모든 연산은 왕복을 검증하는 속성 기반 테스트를 **반드시** 갖춘다. 다음을 포함하되 이에 한정하지 않는다:
- 직렬화 / 역직렬화 (JSON, XML, Protobuf, 바이너리 형식)
- 인코딩 / 디코딩 (Base64, URL 인코딩, 압축)
- 파싱 / 포매팅 (날짜 파싱, 숫자 포매팅, 구조화된 입력을 쓰는 템플릿 렌더링)
- 암호화 / 복호화 (키를 쓸 수 있는 경우)
- 데이터베이스 쓰기 / 읽기 (I/O 자체가 아닌 데이터 변환 계층 대상)
- 모든 유효한 `x` 에 대해 `f_inverse(f(x)) = x` 인 모든 함수 쌍

속성 기반 테스트는 도메인에 맞는 생성기 (PBT-07 참조) 로 무작위 유효 입력을 **반드시** 생성하고, 왕복 결과가 원래 입력과 같은 값인지 단언 (assert) 한다.

**검증**:
- 모든 직렬화 / 역직렬화 쌍에 왕복 속성 테스트가 있음
- 모든 인코딩 / 디코딩 쌍에 왕복 속성 테스트가 있음
- 모든 파싱 / 포매팅 쌍에 왕복 속성 테스트가 있음 (또는 변환이 손실성인 이유를 문서화함)
- 왕복 테스트가 하드코딩된 예시가 아닌 생성된 입력을 사용함
- 손실성 변환 (예: 정밀도가 손실되는 실수 포매팅) 은 허용 오차를 문서화하고 그 오차 안에서 테스트함

## Rule PBT-03: 불변 조건 속성 (Invariant Properties)

**규칙**: 문서화된 불변 조건이 있는 함수는 생성된 입력 전반에서 그 불변 조건이 성립하는지 검증하는 속성 기반 테스트를 **반드시** 갖춘다. 흔한 불변 조건:
- **크기 보존**: 출력 컬렉션의 크기가 입력과 같다 (예: map, sort)
- **원소 보존**: 출력이 입력과 정확히 같은 원소를 포함하며 순서만 바뀔 수 있다 (예: sort, shuffle)
- **순서 보장**: 출력이 순서 제약을 만족한다 (예: sort 결과는 감소하지 않는 순서)
- **범위 제약**: 출력 값이 정의된 범위 안에 있다 (예: normalize 결과는 [0, 1] 범위)
- **타입 보존**: 모든 유효한 입력에 대해 출력 타입이 기대 타입과 일치한다
- **비즈니스 규칙 불변 조건**: 항상 성립해야 하는 도메인 규칙 (예: "유효한 거래 후 계좌 잔액은 절대 음수가 되지 않는다", "할인액은 상품 가격을 절대 넘지 않는다")

**검증**:
- 문서화된 각 불변 조건에 대응하는 속성 기반 테스트가 있음
- 불변 조건 테스트가 경계 값을 포함한 넓은 범위의 입력을 생성함
- functional design 에서 식별한 비즈니스 규칙 불변 조건이 PBT 로 다뤄짐
- 불변 조건 테스트가 예시 기반 테스트의 단언을 그대로 중복하지 않음 — 특정 사례가 아닌 일반 규칙을 테스트함

## Rule PBT-04: 멱등성 속성 (Idempotency Properties)

**규칙**: 멱등성을 내세우거나 요구하는 모든 연산은 이를 증명하는 속성 기반 테스트를 **반드시** 갖춘다. 테스트는 생성된 모든 유효 입력에 대해 `f(f(x)) = f(x)` 임을 **반드시** 검증한다. 적용 대상:
- 멱등으로 문서화된 API 엔드포인트 (PUT, DELETE)
- 데이터 정규화 또는 정화 (sanitization) 함수
- 캐시 채우기 연산
- 중복 제거 로직
- 설정 적용 (설정을 두 번 적용해도 상태가 바뀌지 않아야 함)
- 최소 1회 전달 (at-least-once delivery) 시스템의 메시지 처리

**검증**:
- 멱등으로 문서화된 모든 연산에 `f(f(x)) = f(x)` 를 단언하는 PBT 가 있음
- 멱등성 테스트가 (기본 타입만이 아닌) 도메인에 맞는 생성기를 사용함
- 상태를 가진 연산은 1회 적용과 반복 적용 후 관찰 가능한 상태가 같은지 검증함

## Rule PBT-05: 오라클 및 모델 기반 테스트 (Oracle and Model-Based Testing)

**규칙**: 참조 구현, 단순화한 모델, 또는 정확성이 알려진 알고리즘이 있으면, 속성 기반 테스트는 테스트 대상 시스템을 오라클과 **반드시** 비교한다. 적용 대상:
- 알려진 무차별 대입 버전을 대체하는 최적화 알고리즘
- 기존 (legacy) 구현을 대체하는 리팩터링 코드
- 순차 버전과 비교하는 병렬 / 동시성 구현
- 잘 알려진 알고리즘 (정렬, 탐색, 그래프 순회) 의 자체 구현
- 참조 데이터베이스와 비교하는 새 쿼리 엔진

속성 기반 테스트는 무작위 유효 입력을 **반드시** 생성하고, 생성된 모든 입력에 대해 테스트 대상 시스템이 오라클과 동등한 결과를 내는지 단언한다.

**검증**:
- 참조 구현이 있거나 쉽게 작성할 수 있으면 오라클 PBT 가 있음
- 오라클 테스트가 정상, 경계, 적대적 사례를 아우르는 다양한 입력을 생성함
- 동등성이 정확히 정의됨 (완전 일치, 구조적 일치, 또는 문서화된 허용 오차)
- 오라클이 없으면 근거와 함께 이 규칙을 N/A 로 표시함

---

## Rule PBT-06: 상태 기반 속성 테스트 (Stateful Property Testing)

**규칙**: 변경 가능한 상태를 관리하는 구성요소는 상태 기반 속성 테스트 대상인지 **반드시** 평가한다. 상태 기반 PBT 는 시스템에 대한 무작위 명령 (연산) 순서를 생성하고 각 단계 후 불변 조건이 성립하는지 검증한다. 적용 대상:
- 메모리 내 캐시와 데이터 저장소
- 상태 머신과 워크플로 엔진
- 큐와 버퍼 구현
- 세션 관리 시스템
- 장바구니, 주문 파이프라인 및 이와 비슷한 상태를 가진 비즈니스 객체
- 연산 결과가 이전 연산에 따라 달라지는 모든 구성요소

상태 기반 PBT 는 **반드시** 다음을 지킨다:
- 테스트 대상 시스템을 본뜬 단순화한 모델 (참조 상태) 을 정의한다
- 유효한 명령 (추가, 삭제, 수정, 조회 등) 의 무작위 순서를 생성한다
- 각 명령을 실제 시스템과 모델 양쪽에 실행한다
- 각 명령 후 관찰 가능한 상태나 조회 결과가 시스템과 모델 간에 일치하는지 단언한다
- 빈 순서를 포함해 다양한 길이의 순서를 테스트한다

**검증**:
- functional design 에서 식별한 상태를 가진 구성요소에 상태 기반 PBT 가 있거나, 해당하지 않는 이유를 문서화함
- 비교용 단순화 모델이 정의됨
- 명령 생성기가 현실적인 파라미터 분포로 유효한 연산 순서를 생성함
- 불변 조건을 순서 끝에서만이 아니라 각 명령 후에 확인함
- 상태를 가진 구성요소가 없으면 이 규칙을 N/A 로 표시함

## Rule PBT-07: 생성기 품질 (Generator Quality)

**규칙**: 속성 기반 테스트는 기본 타입만이 아닌, 현실적이고 구조화된 입력을 만드는 도메인 전용 생성기를 **반드시** 사용한다. 질 낮은 생성기 (예: 이메일 필드에 무작위 문자열, 나이 필드에 범위 제한 없는 정수) 는 의미 없는 테스트 사례를 만들고 실제 버그를 놓친다.

생성기 요구사항:
- **도메인 타입**: 비즈니스 제약 (유효한 이메일 형식, 양수 금액, 유효한 날짜 범위) 을 지키는 도메인 객체 (예: User, Order, Transaction) 용 사용자 정의 생성기를 **반드시** 만든다
- **제약된 기본 타입**: 도메인이 요구하는 곳에서는 숫자 생성기를 현실적인 범위로 **반드시** 제한한다
- **구조화된 데이터**: 복잡한 입력 (중첩 객체, 도메인 객체 목록) 용 생성기는 구조적으로 유효한 데이터를 **반드시** 만든다
- **경계 사례 포함**: 생성기는 정상 값과 함께 경계 값 (빈 컬렉션, 0, 최댓값, 유니코드 문자열) 을 포함하도록 설정하는 것이 바람직하다 (SHOULD)
- **재사용성**: 도메인 생성기는 테스트 파일마다 중복하지 말고 재사용 가능한 테스트 유틸리티로 정의하는 것이 바람직하다 (SHOULD)

**검증**:
- 도메인 타입 파라미터에 원시 기본 타입 생성기만 (예: `st.integers()` 단독) 쓰는 PBT 가 없음
- PBT 에서 쓰는 도메인 객체용 사용자 정의 생성기가 있음
- 생성기가 문서화된 비즈니스 제약 (예: 양수 금액, 유효한 형식) 을 지킴
- 여러 테스트가 같은 도메인 타입을 공유하는 곳에서는 생성기 정의가 한곳에 모여 있고 재사용 가능함

---

## Rule PBT-08: 축소 및 재현성 (Shrinking and Reproducibility)

**규칙**: 모든 속성 기반 테스트는 축소 (shrinking) 와 결정적 재현성을 **반드시** 지원한다.

- **축소**: 속성이 실패하면 PBT 프레임워크가 실패 입력을 최소 재현 사례로 **반드시** 자동 축소한다. 문서화된 기술적 이유 (예: 통합 테스트에서 축소가 외부 서비스 호출과 양립하지 않음) 가 없으면, 테스트는 프레임워크의 축소 기능을 **절대** 끄거나 우회하지 않는다 (MUST NOT).
- **재현성**: 모든 PBT 실행은 seed 값으로 **반드시** 재현 가능해야 한다. 실패한 시나리오를 그대로 다시 실행할 수 있도록 실패 시 seed 를 **반드시** 기록한다. CI 설정은 결정적 실행을 위해 고정 seed 를 쓰거나, 실패 후 재현을 위해 매 실행마다 무작위 seed 를 기록하는 방식 중 하나를 **반드시** 택한다.
- **CI 통합**: PBT 는 프로젝트의 CI 파이프라인에 **반드시** 포함한다. 불안정한 (flaky) PBT 실패 (코드 변경 없이 재시도하면 통과하는 테스트) 는 억누르지 말고 **반드시** 조사한다.

**검증**:
- PBT 프레임워크의 축소 기능이 켜져 있음 (재정의되거나 꺼지지 않음)
- 실패 시 테스트 출력에 seed 값과 축소된 최소 실패 입력이 포함됨
- CI 설정이 모든 PBT 실행의 seed 를 기록하거나 고정 seed 를 사용함
- 문서화된 근거 없이 CI 에서 제외된 PBT 가 없음
- 불안정한 PBT 실패를 조용히 재시도하지 않고 추적 · 조사함

---

## Rule PBT-09: 프레임워크 선택 (Framework Selection)

**규칙**: 프로젝트는 주 언어에 맞는 속성 기반 테스트 프레임워크를 **반드시** 선택하고 설정한다. 프레임워크는 다음을 **반드시** 지원한다:
- 도메인 타입용 사용자 정의 생성기 / 전략 (strategy)
- 실패 사례 자동 축소
- seed 기반 재현성
- 프로젝트의 기존 테스트 실행기와 통합

언어별 권장 프레임워크 (전체 목록 아님):

| 언어 | 프레임워크 | 비고 |
|---|---|---|
| Python | Hypothesis | 성숙함, 축소 기능 우수, Django 통합 |
| JavaScript / TypeScript | fast-check | Jest, Vitest, Mocha 와 통합 |
| Java | jqwik | JUnit 5 통합, 상태 기반 테스트 지원 |
| Kotlin | Kotest Property Testing | Kotest 프레임워크 통합 |
| Scala | ScalaCheck | SBT 통합, 널리 쓰임 |
| Rust | proptest | 매크로 기반, 축소 기능 좋음 |
| Go | rapid | 가벼움, Go 다운 방식 |
| Haskell | QuickCheck | 최초의 PBT 프레임워크 |
| C# / .NET | FsCheck | xUnit, NUnit 과 함께 동작 |
| Erlang / Elixir | PropEr / StreamData | OTP 인지, 상태 기반 테스트 |

선택한 프레임워크는 기술 스택 결정에 **반드시** 문서화하고 프로젝트 의존성에 포함한다.

**검증**:
- PBT 프레임워크가 선택되어 기술 스택 결정에 문서화됨
- 프레임워크가 프로젝트 의존성 (package.json, pom.xml, requirements.txt 등) 에 포함됨
- 프레임워크가 사용자 정의 생성기, 축소, seed 기반 재현성을 지원함
- 프로젝트가 여러 언어를 쓰면, PBT 적용 대상 코드가 있는 언어마다 프레임워크가 선택됨

---

## Rule PBT-10: 상호 보완적 테스트 전략 (Complementary Testing Strategy)

**규칙**: 속성 기반 테스트는 예시 기반 테스트를 대체하지 않고 **반드시** 보완한다. 두 방식은 목적이 다르다:

- **예시 기반 테스트**: 구체적으로 알려진 시나리오, 회귀 사례, 비즈니스상 중요한 경계 사례를 명시적 기대값과 함께 문서화한다. 구체적 동작을 실행 가능한 문서로 남기는 역할을 한다.
- **속성 기반 테스트**: 넓은 입력 공간에서 일반적인 불변 조건을 검증한다. 알려지지 않은 경계 사례를 찾고 속성이 보편적으로 성립하는지 확인한다.

요구사항:
- user story 나 요구사항에서 식별한 중요한 비즈니스 시나리오는, 같은 속성을 PBT 가 다루더라도 명시적 예시 기반 테스트를 **반드시** 갖춘다
- PBT 는 비즈니스상 중요한 경로의 유일한 테스트가 **절대** 되어서는 안 된다 (MUST NOT) — 주요 시나리오는 최소 1개의 예시 기반 테스트로 기대 동작을 고정해야 한다
- PBT 가 실패 사례를 찾으면, 축소된 최소 예시를 영구적인 예시 기반 회귀 테스트로 추가하는 것이 바람직하다 (SHOULD)
- 테스트 문서는 예시 기반 테스트와 속성 기반 테스트를 **반드시** 명확히 구분한다 (별도 테스트 파일, 테스트 클래스, 또는 이름으로 구분되는 테스트 함수)

**검증**:
- 비즈니스상 중요한 경로에 예시 기반 테스트와 속성 기반 테스트가 모두 있음
- 어떤 중요 기능도 PBT 만으로 테스트 범위를 채우지 않음
- 테스트 파일이나 테스트 클래스가 PBT 와 예시 기반 테스트를 명확히 분리하거나 표시함
- PBT 로 발견한 실패의 회귀 테스트가 영구적인 예시 기반 테스트로 남아 있음

---

## 강제 적용 통합 (Enforcement Integration)

이 규칙은 다음 AI-DLC stage 에 적용되는 공통 제약이다:

| Stage | 적용 규칙 | 강제 내용 |
|---|---|---|
| Functional Design | PBT-01 | 설계 산출물에 속성 식별이 들어가야 함 |
| NFR Requirements | PBT-09 | 기술 스택 결정에 프레임워크 선택이 포함되어야 함 |
| Code Generation (Planning) | PBT-01 ~ PBT-10 | 코드 생성 계획에 식별한 속성에 대한 PBT 테스트 단계가 포함되어야 함 |
| Code Generation (Generation) | PBT-02 ~ PBT-08, PBT-10 | 생성된 테스트에 예시 기반 테스트와 함께 PBT 가 포함되어야 함 |
| Build and Test | PBT-08 | 테스트 실행 안내에 seed 기록과 CI 통합을 포함한 PBT 가 들어가야 함 |

적용 대상인 각 stage 에서:
- 생성된 산출물에 대해 모든 PBT 규칙의 검증 기준을 평가한다
- stage 완료 요약에 "PBT 준수 (PBT Compliance)" 섹션을 넣어 각 규칙을 준수 (compliant), 미준수 (non-compliant), N/A 로 나열한다
- 미준수 규칙이 하나라도 있으면 차단성 PBT 발견 사항이다 — 개요에서 정의한 차단성 발견 사항 처리를 따른다
- 설계 문서와 테스트 안내에 PBT 규칙 참조를 포함한다

## 부록: 속성 분류 빠른 참조 (Appendix: Property Category Quick Reference)

Functional Design (PBT-01) 에서 속성을 식별하는 개발자와 AI 모델용:

| 패턴 이름 | 정식 용어 | 테스트 형태 | 사용 시점 |
|---|---|---|---|
| 갔다가 다시 돌아오기 (There and back again) | 역함수 (Invertible function) | `f_inv(f(x)) == x` | 직렬화, 인코딩, 파싱 |
| 어떤 것은 절대 변하지 않는다 (Some things never change) | 불변 조건 (Invariant) | `measure(f(x)) == measure(x)` | 정렬, map, filter, 변환 |
| 변할수록 그대로다 (The more things change, the more they stay the same) | 멱등성 (Idempotence) | `f(f(x)) == f(x)` | 정규화, 중복 제거, 캐시 쓰기 |
| 길은 달라도 도착지는 같다 (Different paths, same destination) | 교환 법칙 (Commutativity) | `f(g(x)) == g(f(x))` | 산술, 집합 연산, 독립적인 변환 |
| 작은 문제부터 풀기 (Solve a smaller problem first) | 구조적 귀납 (Structural induction) | `x` 에 대한 속성이 `x + element` 에 대한 속성을 함의 | 재귀 구조, 리스트, 트리 |
| 증명은 어렵고 검증은 쉽다 (Hard to prove, easy to verify) | 검증 (Verification) | `verify(solve(x)) == true` | 풀이기, 최적화기, 탐색 알고리즘 |
| 테스트 오라클 (The test oracle) | 참조 비교 (Reference comparison) | `f(x) == oracle(x)` | 최적화 vs 무차별 대입, 리팩터링 vs 기존 구현 |

출처: 속성 분류 체계는 Scott Wlaschin 의 "Choosing properties for property-based testing" ([fsharpforfunandprofit.com](https://fsharpforfunandprofit.com/posts/property-based-testing-2/)) 을 바탕으로 함.
