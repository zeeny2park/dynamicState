# 기본 보안 규칙 (Baseline Security Rules)

## 개요
이 보안 규칙은 모든 AI-DLC phase 에 걸쳐 적용되는 **필수 (MANDATORY)** 공통 제약이다. 선택적 지침이 아니라, 각 stage 가 질문 생성, 설계 산출물 작성, 코드 생성, 완료 메시지 제시 시 **반드시** 강제해야 하는 엄격한 제약이다.

**강제 (Enforcement)**: 적용 대상인 각 stage 에서 모델은 사용자에게 stage 완료 메시지를 제시하기 전에 이 규칙의 준수 여부를 **반드시** 검증한다.

### 차단성 보안 발견 사항 처리 (Blocking Security Finding Behavior)
**차단성 보안 발견 사항 (blocking security finding)** 의 의미:
1. 해당 발견 사항은 stage 완료 메시지의 "보안 발견 사항 (Security Findings)" 섹션에 SECURITY 규칙 ID 및 설명과 함께 **반드시** 나열한다
2. 모든 차단성 발견 사항이 해결될 때까지 stage 는 "다음 Stage 로 진행 (Continue to Next Stage)" 선택지를 **절대** 제시하지 않는다 (MUST NOT)
3. 모델은 무엇을 바꿔야 하는지 명확한 설명과 함께 "변경 요청 (Request Changes)" 선택지만 **반드시** 제시한다
4. 해당 발견 사항은 SECURITY 규칙 ID, 설명, stage 맥락과 함께 `aidlc-docs/audit.md` 에 **반드시** 기록한다

SECURITY 규칙이 현재 프로젝트에 해당하지 않으면 (예: 데이터 저장소가 없는데 SECURITY-01), 준수 요약에 **N/A** 로 표시한다 — 이는 차단성 발견 사항이 아니다.

### 기본 강제 수준 (Default Enforcement)
이 문서의 모든 규칙은 기본적으로 **차단성 (blocking)** 이다. 어떤 규칙의 검증 기준이라도 충족되지 않으면 차단성 보안 발견 사항이며 — 위에서 정의한 차단성 발견 사항 처리를 따른다.

### 검증 기준 형식 (Verification Criteria Format)
이 문서의 검증 항목은 준수 여부 점검을 설명하는 일반 글머리 기호 목록이다. stage 계획 파일에서 진행 추적용으로 쓰는 `- [ ]` / `- [x]` 체크박스와는 별개다. 각 항목은 검토 시 준수 또는 미준수로 평가한다.

## Rule SECURITY-01: 저장 데이터 및 전송 구간 암호화 (Encryption at Rest and in Transit)

**규칙**: 모든 데이터 영속 저장소 (데이터베이스, 객체 스토리지, 파일 시스템, 캐시 또는 이에 준하는 모든 것) 는 다음을 **반드시** 갖춘다:
- 관리형 키 서비스 또는 고객 관리형 키를 사용한 저장 데이터 암호화 (encryption at rest) 활성화
- 전송 구간 암호화 (encryption in transit) 강제 (저장소로 들어오고 나가는 모든 데이터 이동에 TLS 1.2 이상)

**검증**:
- 암호화 설정 블록 없이 정의된 스토리지 리소스가 없음
- 암호화되지 않은 프로토콜을 쓰는 데이터베이스 연결 문자열이 없음
- 객체 스토리지가 저장 데이터 암호화를 강제하고 정책으로 비 TLS 요청을 거부함
- 데이터베이스 인스턴스에 스토리지 암호화가 활성화되어 있고 TLS 연결을 강제함

---

## Rule SECURITY-02: 네트워크 중계 구성요소의 접근 로깅 (Access Logging on Network Intermediaries)

**규칙**: 외부 트래픽을 처리하는 모든 네트워크 대면 중계 구성요소는 접근 로깅을 **반드시** 활성화한다. 대상:
- 로드 밸런서 → 영속 저장소로 접근 로그 기록
- API 게이트웨이 → 중앙 로그 서비스로 실행 로깅 및 접근 로깅
- CDN 배포 → 표준 로깅 또는 실시간 로그

**검증**:
- 접근 로깅 없이 정의된 로드 밸런서 리소스가 없음
- 접근 로깅 설정 없이 정의된 API 게이트웨이 stage 가 없음
- 로깅 설정 없이 정의된 CDN 배포가 없음

---

## Rule SECURITY-03: 애플리케이션 수준 로깅 (Application-Level Logging)

**규칙**: 배포되는 모든 애플리케이션 구성요소는 구조화된 로깅 기반을 **반드시** 포함한다:
- 로깅 프레임워크를 **반드시** 설정한다
- 로그 출력은 중앙 로그 서비스로 **반드시** 보낸다
- 로그에는 타임스탬프, 상관관계 ID / 요청 ID, 로그 수준, 메시지를 **반드시** 포함한다
- 민감 데이터 (비밀번호, 토큰, 개인식별정보 (PII)) 는 로그 출력에 **절대** 나타나지 않는다 (MUST NOT)

**검증**:
- 모든 서비스 / 함수 진입점에 설정된 logger 가 포함됨
- 운영 코드에서 임시 로그 문장을 주 로깅 수단으로 쓰지 않음
- 로그 설정이 출력을 중앙 로그 서비스로 보냄
- 비밀 정보, 토큰, PII 를 로그로 남기지 않음

---

## Rule SECURITY-04: 웹 애플리케이션 HTTP 보안 헤더 (HTTP Security Headers for Web Applications)

**규칙**: HTML 을 제공하는 모든 엔드포인트에 다음 HTTP 응답 헤더를 **반드시** 설정한다:

| 헤더 | 필수 값 |
|---|---|
| `Content-Security-Policy` | 제한적인 정책 정의 (최소: `default-src 'self'`) |
| `Strict-Transport-Security` | `max-age=31536000; includeSubDomains` |
| `X-Content-Type-Options` | `nosniff` |
| `X-Frame-Options` | `DENY` (프레임 삽입이 필요하면 `SAMEORIGIN`) |
| `Referrer-Policy` | `strict-origin-when-cross-origin` |

**참고**: `X-XSS-Protection` 은 최신 브라우저에서 폐기되었다. 대신 `Content-Security-Policy` 를 사용한다.

**검증**:
- 미들웨어 또는 응답 인터셉터가 필수 헤더를 모두 설정함
- CSP 정책이 문서화된 근거 없이 `unsafe-inline` 또는 `unsafe-eval` 을 쓰지 않음
- HSTS max-age 가 최소 31536000 (1년)

---

## Rule SECURITY-05: 모든 API 파라미터 입력 검증 (Input Validation on All API Parameters)

**규칙**: 모든 API 엔드포인트 (REST, GraphQL, gRPC, WebSocket) 는 처리 전에 모든 입력 파라미터를 **반드시** 검증한다. 검증에는 다음을 **반드시** 포함한다:
- **타입 검사**: 예상치 못한 타입 거부
- **길이 / 크기 한도**: 문자열 최대 길이, 배열 및 payload 최대 크기 강제
- **형식 검증**: 구조화된 입력 (이메일, 날짜, ID) 에 허용 목록 (정규식 또는 스키마) 사용
- **정화 (Sanitization)**: XSS 방지를 위해 사용자 입력 문자열의 HTML / 스크립트 내용을 이스케이프하거나 거부
- **인젝션 방지**: 모든 데이터베이스 작업에 파라미터화된 쿼리 사용 (문자열 연결 금지)

**검증**:
- 모든 API 핸들러가 검증 라이브러리 또는 스키마를 사용함
- 가공하지 않은 사용자 입력을 SQL, NoSQL, OS 명령에 연결하지 않음
- 문자열 입력에 명시적 최대 길이 제약이 있음
- 요청 본문 크기 한도가 프레임워크 또는 게이트웨이 수준에서 설정됨

---

## Rule SECURITY-06: 최소 권한 접근 정책 (Least-Privilege Access Policies)

**규칙**: 모든 ID 및 접근 관리 (IAM) 정책, 역할, 권한 경계는 최소 권한 원칙을 **반드시** 따른다:
- 구체적인 리소스 식별자 사용 — API 가 리소스 수준 권한을 지원하지 않는 경우가 아니면 와일드카드 리소스를 **절대** 쓰지 않는다 (예외는 문서화)
- 구체적인 작업 (action) 사용 — 와일드카드 작업을 **절대** 쓰지 않는다
- 가능한 곳에는 조건으로 범위를 제한한다
- 읽기 권한과 쓰기 권한을 별도의 정책 문장으로 분리한다

**검증**:
- 문서화된 예외 없이 와일드카드 작업이나 와일드카드 리소스를 포함한 정책이 없음
- 서비스가 실제로 호출하는 것보다 넓은 권한을 가진 서비스 역할이 없음
- 가능한 곳에서는 인라인 정책 대신 관리형 정책을 사용함
- 모든 역할에 특정 서비스 또는 계정으로 범위가 제한된 신뢰 정책이 있음

---

## Rule SECURITY-07: 제한적인 네트워크 구성 (Restrictive Network Configuration)

**규칙**: 모든 네트워크 구성 (보안 그룹, 네트워크 ACL, 라우팅 테이블) 은 기본 거부 (deny-by-default) 를 **반드시** 따른다:
- 방화벽 규칙: 애플리케이션에 필요한 특정 포트만 연다
- 80/443 포트의 공개 로드 밸런서를 제외하면 출발지 `0.0.0.0/0` 인바운드 규칙 없음
- 명시적 근거가 없으면 모든 포트에 대한 `0.0.0.0/0` 아웃바운드 규칙 없음
- 프라이빗 서브넷은 인터넷 게이트웨이로 가는 직접 경로를 **절대** 갖지 않는다 (MUST NOT)
- 가능한 곳에서는 클라우드 서비스 접근에 프라이빗 엔드포인트를 사용한다

**검증**:
- 공개 로드 밸런서의 80/443 외 포트에서 인바운드 `0.0.0.0/0` 을 허용하는 방화벽 규칙이 없음
- 데이터베이스 및 애플리케이션 방화벽 규칙이 출발지를 특정 CIDR 블록 또는 보안 그룹 참조로 제한함
- 프라이빗 서브넷이 (인터넷 게이트웨이가 아닌) NAT 게이트웨이를 거쳐 라우팅됨
- 트래픽이 많은 클라우드 서비스 호출에 프라이빗 엔드포인트를 사용함

---

## Rule SECURITY-08: 애플리케이션 수준 접근 제어 (Application-Level Access Control)

**규칙**: 리소스에 접근하거나 리소스를 변경하는 모든 애플리케이션 엔드포인트는 애플리케이션 계층에서 권한 검사를 **반드시** 강제한다:
- **기본 거부**: 명시적으로 공개 표시된 경우가 아니면 모든 경로 / 엔드포인트가 인증을 **반드시** 요구한다
- **객체 수준 권한 검사**: ID 로 리소스를 참조하는 모든 요청은 요청한 사용자 / 주체가 그 리소스를 소유하거나 접근 권한이 있는지 **반드시** 확인한다 (IDOR 방지)
- **기능 수준 권한 검사**: 관리자 또는 특권 작업은 호출자의 역할 / 권한을 서버 측에서 **반드시** 확인한다 — 클라이언트 측 숨김에 절대 의존하지 않는다
- **CORS 정책**: 교차 출처 리소스 공유 (CORS) 는 명시적으로 허용한 출처로 **반드시** 제한한다 — 인증이 필요한 엔드포인트에 `Access-Control-Allow-Origin: *` 를 절대 쓰지 않는다
- **토큰 검증**: JWT 또는 세션 토큰은 모든 요청마다 서버 측에서 **반드시** 검증한다 (서명, 만료, audience, issuer)

**검증**:
- 모든 컨트롤러 / 핸들러에 권한 미들웨어 또는 가드가 적용됨
- 호출자의 소유권이나 권한을 확인하지 않고 리소스 ID 에 대한 데이터를 반환하는 엔드포인트가 없음
- 관리자 / 특권 경로에 서버 측에서 강제되는 명시적 역할 검사가 있음
- 인증이 필요한 엔드포인트의 CORS 설정에 와일드카드 출처를 쓰지 않음
- 토큰 검증이 (로그인 시점만이 아니라) 모든 요청마다 서버 측에서 이루어짐

## Rule SECURITY-09: 보안 강화 및 잘못된 구성 방지 (Security Hardening and Misconfiguration Prevention)

**규칙**: 배포되는 모든 구성요소는 강화 기준 (hardening baseline) 을 **반드시** 따른다:
- **기본 자격 증명 금지**: 기본 사용자 이름 / 비밀번호는 배포 전에 **반드시** 변경하거나 비활성화한다
- **최소 설치**: 쓰지 않는 기능, 프레임워크, 샘플 애플리케이션, 문서 엔드포인트를 제거하거나 비활성화한다
- **오류 처리**: 운영 환경의 오류 응답은 최종 사용자에게 스택 트레이스, 내부 경로, 프레임워크 버전, 데이터베이스 세부 정보를 **절대** 노출하지 않는다 (MUST NOT)
- **디렉터리 목록**: 웹 서버는 디렉터리 목록 표시를 **반드시** 비활성화한다
- **클라우드 스토리지**: 클라우드 객체 스토리지는 명시적으로 필요하고 문서화된 경우가 아니면 공개 접근을 **반드시** 차단한다
- **패치 관리**: 런타임 환경, 프레임워크, OS 이미지는 현재 지원되는 버전을 **반드시** 사용한다

**검증**:
- 설정 파일, 환경 변수, IaC 템플릿에 기본 자격 증명이 없음
- 운영 환경 오류 응답이 일반적인 메시지를 반환함 (스택 트레이스나 내부 세부 정보 없음)
- 문서화된 예외가 없으면 클라우드 객체 스토리지의 공개 접근이 차단됨
- 샘플 / 데모 애플리케이션이나 기본 페이지가 배포되지 않음
- 프레임워크 및 런타임 버전이 최신이고 지원됨


---

## Rule SECURITY-10: 소프트웨어 공급망 보안 (Software Supply Chain Security)

**규칙**: 모든 프로젝트는 소프트웨어 공급망을 **반드시** 관리한다:
- **의존성 고정**: 모든 의존성은 정확한 버전 또는 lock 파일을 **반드시** 사용한다
- **취약점 스캔**: 의존성 취약점 스캐너를 **반드시** 설정한다 
- **미사용 의존성 금지**: 실제로 쓰지 않는 패키지는 제거한다
- **신뢰할 수 있는 출처만**: 의존성은 공식 레지스트리 또는 검증된 사설 레지스트리에서 **반드시** 가져온다 — 검증되지 않은 제3자 출처 금지
- **SBOM**: 운영 배포에 대해 소프트웨어 자재 명세서 (Software Bill of Materials) 를 **반드시** 생성한다
- **CI/CD 무결성**: 빌드 파이프라인은 고정된 도구 버전과 검증된 베이스 이미지를 **반드시** 사용한다 — 운영용 Dockerfile 이나 CI 설정에 `latest` 태그 금지

**검증**:
- lock 파일이 존재하고 버전 관리에 commit 되어 있음
- 의존성 취약점 스캔 단계가 CI/CD 에 포함되거나 빌드 안내에 문서화됨
- 쓰지 않거나 방치된 의존성이 포함되지 않음
- 운영용 Dockerfile 과 CI 설정이 `latest` 또는 고정되지 않은 이미지 태그를 쓰지 않음
- 의존성을 공식 또는 검증된 레지스트리에서 가져옴

---

## Rule SECURITY-11: 보안 설계 원칙 (Secure Design Principles)

**규칙**: 애플리케이션 설계는 처음부터 보안을 **반드시** 반영한다:
- **관심사 분리**: 보안에 중요한 로직 (인증, 권한 검사, 결제 처리) 은 전용 모듈로 **반드시** 분리한다 — 코드베이스 곳곳에 흩어 두지 않는다
- **심층 방어**: 단일 통제가 유일한 방어선이 되어서는 안 된다 — 통제를 겹겹이 둔다 (검증 + 권한 검사 + 암호화)
- **요청 속도 제한**: 공개 엔드포인트는 남용 방지를 위해 rate limiting 또는 throttling 을 **반드시** 구현한다
- **비즈니스 로직 악용**: 설계는 정상 흐름 (happy-path) 시나리오뿐 아니라 오용 사례도 **반드시** 고려한다

**검증**:
- 보안에 중요한 로직이 전용 모듈 또는 서비스에 캡슐화됨
- 공개 API 에 rate limiting 이 설정됨
- 설계 문서가 최소 1개의 오용 / 악용 시나리오를 다룸

---

## Rule SECURITY-12: 인증 및 자격 증명 관리 (Authentication and Credential Management)

**규칙**: 사용자 인증이 있는 모든 애플리케이션은 다음을 **반드시** 구현한다:
- **비밀번호 정책**: 최소 8자, 유출된 비밀번호 목록과 대조
- **자격 증명 저장**: 비밀번호는 적응형 알고리즘으로 **반드시** 해시한다 — 약하거나 비적응형인 해시는 절대 쓰지 않는다
- **다중 인증 (MFA)**: 관리자 계정에는 MFA 를 **반드시** 지원하고, 모든 사용자에게도 제공하는 것이 바람직하다 (SHOULD)
- **세션 관리**: 세션은 서버 측 만료가 **반드시** 있어야 하고, 로그아웃 시 무효화되며, secure / httpOnly / sameSite 쿠키 속성을 사용한다
- **무차별 대입 방지**: 로그인 엔드포인트는 반복 실패 후 계정 잠금, 점진적 지연, 또는 CAPTCHA 를 **반드시** 구현한다
- **하드코딩된 자격 증명 금지**: 소스 코드나 IaC 템플릿에 비밀번호, API 키, 비밀 정보를 두지 않는다 — 비밀 관리 서비스 (secrets manager) 를 사용한다

**검증**:
- 비밀번호 해시가 적응형 알고리즘을 사용함 (약하거나 비적응형 해시 아님)
- 세션 쿠키에 `Secure`, `HttpOnly`, `SameSite` 속성이 설정됨
- 로그인 엔드포인트에 무차별 대입 방지 (잠금, 지연, 또는 CAPTCHA) 가 있음
- 소스 코드나 설정 파일에 하드코딩된 자격 증명이 없음
- 관리자 계정에 MFA 가 지원됨
- 세션이 로그아웃 시 무효화되고 만료 시간이 정해져 있음

---

## Rule SECURITY-13: 소프트웨어 및 데이터 무결성 검증 (Software and Data Integrity Verification)

**규칙**: 시스템은 소프트웨어와 데이터의 무결성을 **반드시** 검증한다:
- **역직렬화 안전성**: 신뢰할 수 없는 데이터는 검증 없이 **절대** 역직렬화하지 않는다 (MUST NOT) — 안전한 역직렬화 라이브러리나 허용 타입 목록을 사용한다
- **산출물 무결성**: 다운로드한 의존성, 플러그인, 업데이트는 체크섬 또는 디지털 서명으로 **반드시** 검증한다
- **CI/CD 파이프라인 보안**: 빌드 파이프라인은 파이프라인 정의를 수정할 수 있는 사람을 **반드시** 제한한다 — 코드 작성자와 배포 승인자의 역할을 분리한다
- **CDN 및 외부 리소스**: 외부 CDN 에서 불러오는 스크립트나 리소스는 Subresource Integrity (SRI) 해시를 **반드시** 사용한다
- **데이터 무결성**: 중요한 데이터 변경은 **반드시** 감사 가능해야 한다 (누가, 무엇을, 언제 바꿨는지)

**검증**:
- 신뢰할 수 없는 입력을 안전하지 않게 역직렬화하지 않음
- CDN 에서 불러오는 외부 스크립트에 SRI integrity 속성이 포함됨
- CI/CD 파이프라인 정의가 접근 통제되고 변경이 감사 가능함
- 중요한 데이터 변경이 수행자, 타임스탬프, 변경 전 / 후 값과 함께 기록됨

---

## Rule SECURITY-14: 경보 및 모니터링 (Alerting and Monitoring)

**규칙**: 로깅 (SECURITY-02, SECURITY-03) 에 더해, 시스템은 다음을 **반드시** 포함한다:
- **보안 이벤트 경보**: 중요한 보안 이벤트에 대해 경보를 **반드시** 설정한다: 반복된 인증 실패, 권한 상승 시도, 비정상 위치에서의 접근, 권한 검사 실패
- **로그 무결성**: 로그는 추가 전용 (append-only) 또는 변조 탐지가 가능한 저장소에 **반드시** 저장한다 — 애플리케이션 코드가 자기 감사 로그를 삭제하거나 수정할 수 **없어야** 한다 (MUST NOT)
- **로그 보존**: 로그는 애플리케이션의 컴플라이언스 요구에 맞는 최소 기간 동안 **반드시** 보존한다 (기본: 최소 90일)
- **모니터링 대시보드**: 주요 운영 및 보안 지표에 대한 모니터링 대시보드 또는 알람 설정을 **반드시** 정의한다

**검증**:
- 인증 실패와 권한 위반에 대한 경보가 설정됨
- 애플리케이션 로그 그룹에 보존 정책이 설정됨 (최소 90일)
- 애플리케이션 역할에 자기 로그 그룹 / 스트림을 삭제할 권한이 없음
- 보안 관련 이벤트 (로그인 실패, 접근 거부, 권한 변경) 가 경보를 발생시킴

---

## Rule SECURITY-15: 예외 처리 및 안전 실패 기본값 (Exception Handling and Fail-Safe Defaults)

**규칙**: 모든 애플리케이션은 예외 상황을 안전하게 **반드시** 처리한다:
- **포착 및 처리**: 모든 외부 호출 (데이터베이스, API, 파일 I/O) 에는 명시적 오류 처리가 **반드시** 있어야 한다 — 운영 환경에서 처리되지 않은 promise rejection 이나 포착되지 않은 예외 금지
- **닫힌 상태로 실패 (Fail closed)**: 오류 시 시스템은 접근을 거부하거나 작업을 **반드시** 중단한다 — 절대 열린 상태로 실패 (fail open) 하지 않는다
- **리소스 정리**: 오류 경로에서도 리소스 (연결, 파일 핸들, 잠금) 를 **반드시** 해제한다 — try/finally, using 문, 또는 이에 준하는 패턴을 사용한다
- **사용자 대상 오류**: 사용자에게 보이는 오류 메시지는 **반드시** 일반적인 내용이어야 한다 — 내부 세부 정보나 시스템 정보 금지
- **전역 오류 처리기**: 애플리케이션은 처리되지 않은 예외를 포착해 (SECURITY-03 에 따라) 기록하고 안전한 응답을 반환하는 전역 / 최상위 오류 처리기를 **반드시** 갖춘다

**검증**:
- 모든 외부 호출 (DB, HTTP, 파일 I/O) 에 명시적 오류 처리가 있음 (try/catch, .catch(), 오류 콜백)
- 애플리케이션 진입점에 전역 오류 처리기가 설정됨
- 오류 경로가 권한 검사나 검증을 우회하지 않음 (닫힌 상태로 실패)
- 오류 경로에서 리소스가 정리됨 (연결 종료, 트랜잭션 롤백)
- 애플리케이션 코드에 처리되지 않은 promise rejection 이나 포착되지 않은 예외 경고가 없음

## 강제 적용 통합 (Enforcement Integration)

이 규칙은 모든 AI-DLC stage 에 적용되는 공통 제약이다. 각 stage 에서:
- 생성된 산출물에 대해 모든 SECURITY 규칙의 검증 기준을 평가한다
- stage 완료 요약에 "보안 준수 (Security Compliance)" 섹션을 넣어 각 규칙을 준수 (compliant), 미준수 (non-compliant), N/A 로 나열한다
- 미준수 규칙이 하나라도 있으면 차단성 보안 발견 사항이다 — 개요에서 정의한 차단성 발견 사항 처리를 따른다
- 설계 문서와 테스트 안내에 보안 규칙 참조를 포함한다
