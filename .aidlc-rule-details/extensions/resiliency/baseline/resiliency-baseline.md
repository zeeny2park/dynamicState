# 기본 복원력 규칙 (Baseline Resiliency Rules)

## 개요
이 복원력 규칙은 모든 AI-DLC phase 에 걸쳐 적용되는 **필수 (MANDATORY)** 공통 제약이다. 이 규칙은 검증된 클라우드 신뢰성 프레임워크 (AWS Well-Architected Reliability Pillar, 복원력 모범 사례 등) 에서 가져왔으며, 어느 클라우드 제공자의 워크로드에도 적용된다. 규칙은 6개 기둥 (pillar) 으로 구성된다: 비즈니스 목표 (Business Goals), 변경 관리 및 자동화 (Change Management & Automation), 통합 관측 가능성 (Integrated Observability), 고가용성 (High Availability), 재해 복구 (Disaster Recovery), 지속적 개선 (Continuous Improvement).

**적용 (Enforcement)**: 해당되는 각 stage 에서, 모델은 stage 완료 메시지를 사용자에게 보여 주기 전에 **반드시** 이 규칙의 준수 여부를 검증한다.

### 차단 (Blocking) 복원력 발견 사항 처리
**차단 복원력 발견 사항 (blocking resiliency finding)** 이란 다음을 뜻한다:
1. 발견 사항은 **반드시** stage 완료 메시지의 "복원력 발견 사항 (Resiliency Findings)" 절에 RESILIENCY 규칙 ID 와 설명을 함께 적어 나열한다
2. 모든 차단 발견 사항이 해결되기 전까지 stage 는 "다음 Stage 로 진행 (Continue to Next Stage)" 선택지를 **절대** 보여 주지 않는다
3. 모델은 무엇을 바꿔야 하는지 명확한 설명과 함께 "변경 요청 (Request Changes)" 선택지만 **반드시** 보여 준다
4. 발견 사항은 **반드시** `aidlc-docs/audit.md` 에 RESILIENCY 규칙 ID, 설명, stage 맥락과 함께 기록한다

어떤 RESILIENCY 규칙이 현재 프로젝트에 해당하지 않으면 (예: 상태를 가진 데이터가 없을 때의 RESILIENCY-07), 준수 요약에서 **N/A** 로 표시한다 — 이는 차단 발견 사항이 아니다.

### 기본 적용 방식
이 문서의 모든 규칙은 기본적으로 **차단 (blocking)** 규칙이다. 어떤 규칙의 검증 기준이라도 충족되지 않으면 차단 복원력 발견 사항이며, 위에 정의된 차단 발견 사항 처리를 따른다.

### 검증 기준 형식
이 문서의 검증 항목은 준수 점검 내용을 적은 일반 글머리 기호 목록이다. stage 계획 파일에서 진행 상황 추적에 쓰는 `- [ ]` / `- [x]` 체크박스와는 다르다. 각 항목은 검토 중에 준수 또는 미준수로 평가한다.

### 사용자 결정 지점 (모델은 반드시 질문하고, 스스로 결정하지 않는다)
이 확장은 아키텍처 · 프로세스 결정은 LLM 이 아니라 사용자의 몫이라는 AI-DLC 원칙을 따른다. 모델은 아래 규칙에 정의된 확인 질문을 **반드시** 제시하고 사용자의 답을 사용한다 — 사용자를 대신해 말없이 선택해서는 **절대** 안 된다. 사용자에게 명시적으로 넘기는 결정은 다음과 같다:

| 결정 | 규칙 | 제시하는 질문 |
|---|---|---|
| RTO/RPO 목표 및 DR 전략 | RESILIENCY-02 | DR 전략 선택 (Backup&Restore → Active/Active) |
| 변경 관리 프로세스 | RESILIENCY-03 | 기존 조직 프로세스 사용 / 제안 / 예외 |
| CI/CD 도구 | RESILIENCY-04 | 기존 파이프라인 사용 / 제안 |
| 롤백 방식 | RESILIENCY-04 | 이전 버전 재배포 / blue-green / canary / DB 고려 / 기존 절차 |
| 배포 방식 | RESILIENCY-04 | direct / rolling / blue-green / canary |
| 리전 구성 | RESILIENCY-08 | 단일 리전 멀티 존 / 멀티 리전 active-passive · active |
| 장애 대응 프로세스 | RESILIENCY-15 | 기존 조직 프로세스 사용 / 제안 |
| 복원력 테스트 방식 | RESILIENCY-14 | 기존 관행 사용 / 제안 / Operations 로 미룸 |

조직에 이미 프로세스 (변경 관리, CI/CD, 장애 대응, DR 테스트) 가 있으면, 모델은 새로 만들지 말고 **반드시** 기존 프로세스를 참조하고 그에 맞춘다.

## PILLAR 1: 비즈니스 목표 (BUSINESS GOALS)

---

## Rule RESILIENCY-01: 핵심 워크로드 식별 및 우선순위 지정

**규칙**: 모든 프로젝트는 핵심 워크로드와 그 비즈니스 영향을 **반드시** 식별하고 문서화한다:
- **워크로드 분류**: 배포 가능한 각 구성 요소는 비즈니스 중요도 (Critical, High, Medium, Low) 로 **반드시** 분류한다
- **비즈니스 영향 분석**: 각 구성 요소가 사용 불가할 때의 영향 (매출 손실, 사용자 영향, 규제상 결과) 을 **반드시** 문서화한다
- **의존 관계 지도**: 핵심 워크로드는 상류 (upstream) · 하류 (downstream) 의존 관계를 **반드시** 식별하고 문서화한다

**검증**:
- 설계 문서에 구성 요소마다 워크로드 중요도 분류가 들어 있다
- Critical · High 우선순위 구성 요소에 대해 사용 불가 시 비즈니스 영향이 문서화되어 있다
- 상류 · 하류 서비스 관계를 보여 주는 의존 관계 지도가 있다

---

## Rule RESILIENCY-02: 가용성 및 복구 목표

**규칙**: 모든 운영 (production) 워크로드는 비즈니스 기대치에 맞춘 가용성 · 복구 목표를 **반드시** 정의한다:
- **SLA 정의**: 목표 가용성 비율을 **반드시** 정의한다 (예: 99.9%, 99.99%)
- **RTO (Recovery Time Objective, 목표 복구 시간)**: 핵심 워크로드마다 허용 가능한 최대 중단 시간을 **반드시** 정의한다
- **RPO (Recovery Point Objective, 목표 복구 시점)**: 영구 상태를 가진 워크로드마다 허용 가능한 최대 데이터 손실 구간을 **반드시** 정의한다
- **정합성**: 가용성 목표는 비즈니스 요구사항에 비추어 **반드시** 검증한다 — 과잉 설계와 과소 설계 모두 발견 사항이다

**검증**:
- 핵심 워크로드마다 SLA 목표가 문서화되어 있다
- 핵심 워크로드마다 RTO 가 정의 · 문서화되어 있다
- 영구 데이터를 가진 워크로드마다 RPO 가 정의 · 문서화되어 있다
- 목표가 임의가 아니라 비즈니스 요구사항으로 뒷받침된다

**후속 질문 (요구사항 확정 전에 질문)**:

Requirements phase 를 확정하기 전에, 모델은 복구 목표를 파악하고 재해 복구 (Disaster Recovery) 전략을 정하기 위해 다음 확인 질문을 사용자에게 **반드시** 한다. 사용자의 답은 RESILIENCY-11 의 DR 전략 선택과 RESILIENCY-12 의 데이터 보호 결정을 직접 좌우한다.

```markdown
## Question: RTO/RPO 목표와 재해 복구 전략 (RTO/RPO Goals and Disaster Recovery Strategy)
목표 복구 시간 (RTO) 과 목표 복구 시점 (RPO) 은 어느 정도입니까? 이 값에 따라 알맞은 재해 복구 전략과 인프라 이중화 수준이 정해집니다.

A) RPO/RTO: 수 시간 — Backup & Restore 전략. 최저 비용 ($). 데이터는 백업, 서비스는 미배포. 장애 시 IaC 로 재배포하고 백업에서 복원. 핵심이 아닌 워크로드에 적합.

B) RPO/RTO: 수십 분 — Pilot Light 전략. 비용: $$. 데이터는 실시간 유지, 서비스는 대기. 인프라는 배포되어 있으나 실행되지 않으며, failover 시 확장. 중요한 워크로드에 적합.

C) RPO/RTO: 수 분 — Warm Standby 전략. 비용: $$$. 데이터는 실시간 유지, 서비스는 축소 용량으로 실행. failover 시 확장. 비즈니스 핵심 애플리케이션에 적합.

D) RPO/RTO: 거의 실시간 — Multi-site Active/Active 전략. 최고 비용 ($$$$). 데이터 실시간 유지, 여러 리전에서 서비스 동시 운영. 미션 크리티컬, 무중단 요구사항에 적합.

E) N/A — 단일 리전 배포로 충분, 리전 간 DR 불필요. 한 리전 안의 멀티 존 가용성에 의존.
```

## PILLAR 2: 변경 관리 및 자동화 (CHANGE MANAGEMENT & AUTOMATION)

---

## Rule RESILIENCY-03: 변경 관리 프로세스

**규칙**: 모든 프로젝트는 변경으로 인한 장애 위험을 최소화하는 변경 관리 프로세스와 **반드시** 연동한다. 기본 전제는 조직에 이미 변경 관리 프로세스가 **있다**는 것이다 — 이 규칙은 프로젝트가 새 프로세스를 만들지 않고, 기존 프로세스를 찾아 그에 맞추도록 한다.

**확인 질문 (Requirements 중에 질문, 답을 가정하지 않음)**:

```markdown
## Question: 변경 관리 프로세스 (Change Management Process)
이 워크로드의 운영 환경 변경은 어떻게 관리해야 합니까? AI-DLC 는 프로세스를 새로 만들지 않고 답변에 맞춰 설계합니다.

A) 기존 조직 변경 관리 프로세스 사용 — 이름 / 도구를 알려 주십시오 (예: ServiceNow, Jira Change, 사내 CAB). AI-DLC 가 이를 참조하고, 배포 산출물이 그 프로세스 (변경 기록, 승인 관문) 에 맞도록 합니다.

B) 아직 정식 프로세스 없음 — AI-DLC 가 팀이 도입할 가벼운 변경 관리 프로세스 (변경 기록 + 승인 + 롤백 메모) 를 제안.

C) N/A — 이 워크로드는 정식 변경 관리 대상에서 제외 (예: 내부 도구). 제외 근거를 문서화.

X) Other (describe after [Answer]: tag below)

[Answer]: 
```

**검증**:
- 변경 관리 프로세스가 이름으로 식별되어 있거나 (기존 조직 프로세스), 사용자 답에 따라 명시적으로 제안 / 제외되어 있다
- 운영 환경 변경이 승인 · 변경 기록에 대해 식별된 프로세스를 참조한다
- 변경 이력 관리 방식이 식별되어 있다 (기존 도구 또는 제안)

**참고**: 사용자가 A 를 선택하면, 모델은 프로세스를 다시 정의해서는 **절대** 안 된다 — 참조만 하고, 산출물 (예: 배포 설정, 런북) 이 그 프로세스와 호환되도록 한다.

## Rule RESILIENCY-04: 자동 배포 및 롤백

**규칙**: 모든 운영 배포는 자동화하는 것이 이상적이며, 롤백 방식은 모델이 추론하지 않고 사용자가 **반드시** 명시적으로 선택한다. 조직에 기존 CI/CD 도구와 배포 관례가 있으면 프로젝트는 **반드시** 이를 재사용한다.

**정의** (모호함 제거용):
- **롤백 (Rollback)**: 배포 실패 후 실행 중인 워크로드를 마지막 정상 상태로 되돌리는, 정해진 방식. 이 규칙은 특정 방식을 가정하지 않는다 — 사용자가 아래에서 선택한다.
- **배포 방식 (Deployment style)**: 변경을 내보내는 전략 (direct/in-place, rolling, blue/green, canary).

**확인 질문 (Requirements 또는 NFR Design 중에 질문, 답을 가정하지 않음)**:

```markdown

A) 기존 CI/CD 파이프라인 사용 — 도구를 알려 주십시오 (예: GitHub Actions, GitLab CI, Jenkins, CodePipeline). AI-DLC 가 이와 호환되는 산출물을 만듭니다.

B) 파이프라인 없음 — AI-DLC 가 선택된 IaC 와 런타임에 맞는 CI/CD 파이프라인 정의를 제안.
```

- IaC 도구가 식별되어 있다 (기존 조직 표준 또는 사용자 선택)
- CI/CD 파이프라인이 식별되어 있거나 (기존), 사용자 답에 따라 제안되어 있다
- 롤백 방식이 사용자에 의해 명시적으로 선택되고 문서화되어 있다 (추론 아님)

## PILLAR 3: 통합 관측 가능성 (INTEGRATED OBSERVABILITY)

---

## Rule RESILIENCY-05: 핵심 워크로드 모니터링 및 경보

**규칙**: 배포된 모든 워크로드는 관측 가능성의 세 기둥 — 지표 (metrics), 로그 (logs), 추적 (traces) — 전반에 걸쳐 **반드시** 모니터링을 구성한다:
- **지표**: 구성 요소마다 핵심 운영 지표 (지연 시간, 오류율, 처리량, 포화도) 를 **반드시** 수집한다
- **로그**: 구조화된 로깅을 **반드시** 구성하고 중앙 로그 서비스로 보낸다
- **추적**: 여러 서비스로 이루어진 분산 시스템은 서비스 경계를 넘는 요청을 추적하도록 분산 추적을 **반드시** 구성한다
- **대시보드**: 워크로드의 핵심 상태 지표를 보여 주는 모니터링 대시보드를 **반드시** 정의한다

**검증**:
- 구성 요소마다 지표 수집이 구성되어 있다 (클라우드 기본 또는 서드파티 관측 플랫폼 사용)
- 구조화된 로그가 중앙 서비스로 전달된다
- 다중 서비스 아키텍처에 분산 추적이 구성되어 있다 (단일 서비스는 N/A)
- 운영 상태 모니터링용 대시보드 정의 또는 설정이 있다

---

## Rule RESILIENCY-06: 상태 점검 (Health Checks)

**규칙**: 모든 운영 구성 요소는 트래픽을 처리할 수 있는 능력을 정확히 반영하는 상태 점검을 **반드시** 구현한다:
- **얕은 상태 점검 (shallow)**: 모든 서비스는 프로세스가 실행 중임을 확인하는 기본 상태 점검 엔드포인트를 **반드시** 노출한다
- **깊은 상태 점검 (deep)**: 핵심 서비스는 하류 의존 대상 (데이터베이스, 캐시, 외부 API) 과의 연결을 확인하는 깊은 상태 점검을 **반드시** 구현한다
- **로드 밸런서 연동**: 비정상 인스턴스에서 트래픽을 자동으로 돌릴 수 있도록, 상태 점검을 로드 밸런서 또는 서비스 디스커버리와 **반드시** 연동한다
- **합성 모니터링 (synthetic monitoring)**: 외부 공개 엔드포인트는 사용자 관점의 가용성 문제를 감지하도록 합성 canary 모니터링을 갖추는 것을 권장한다 (SHOULD)

**검증**:
- 각 서비스가 상태 점검 엔드포인트를 노출한다
- 핵심 서비스의 깊은 상태 점검이 하류 의존 대상 연결을 확인한다
- 상태 점검이 로드 밸런서 또는 라우팅 방식과 연동되어 있다
- 외부 공개 엔드포인트에 합성 모니터링이 구성되어 있다 (또는 해당 없음으로 문서화)

---

## Rule RESILIENCY-07: 복원력 모니터링

**규칙**: 배포된 워크로드의 복원력 태세는 **반드시** 능동적으로 모니터링한다:
- **복원력 평가**: 지속적인 복원력 태세 평가를 위해 워크로드를 복원력 평가 도구 (클라우드 제공자 기본 또는 서드파티) 에 등록하는 것을 권장한다 (SHOULD)
- **경보 구성**: 복원력 저하를 나타내는 상황 (예: 단일 존 운영, 복제 지연, 백업 실패) 에 대해 경보를 **반드시** 구성한다
- **용량 모니터링**: 확장 한계가 장애로 이어지기 전에 감지할 수 있도록, 자동 확장 지표와 용량 사용률을 **반드시** 모니터링한다

**검증**:
- 복원력 전용 경보가 구성되어 있다 (운영 경보만 있는 것이 아님)
- 용량 · 확장 지표가 모니터링된다
- 복원력 평가 도구가 구성되어 있거나 향후 개선 과제로 문서화되어 있다

## Rule RESILIENCY-08: 멀티 존 및 멀티 리전 배포

**규칙**: 운영 워크로드는 명시적으로 선택된 장애 격리 구성 (fault-isolation topology) 을 **반드시** 갖춘다. 운영 환경에는 멀티 존 기준이 필수이며, 멀티 리전 여부는 모델이 추론하지 않고 사용자가 **반드시** 결정한다 (RESILIENCY-02 의 RTO/RPO 답에 따라).

**멀티 존 기준 (운영 환경 필수)**:
- **컴퓨팅**: 컴퓨팅 자원 (VM, 컨테이너 클러스터) 은 최소 2개 가용 영역 (availability zone) 에 **반드시** 분산한다. 서버리스 서비스는 보통 기본적으로 멀티 존이다.
- **데이터 저장소**: 데이터베이스와 캐시는 멀티 존 구성 (복제, 클러스터, 전역 분산) 을 **반드시** 사용한다
- **부하 분산**: 트래픽은 로드 밸런서 또는 DNS 기반 라우팅으로 여러 존에 **반드시** 분산한다
- **정적 안정성 (static stability)**: 존 하나가 사용 불가해져도, 복구를 위해 컨트롤 플레인 작업을 하지 않고도 아키텍처가 **반드시** 계속 동작한다

**멀티 리전 결정 (사용자 결정 — 추론 금지)**:

단일 리전 멀티 존과 멀티 리전 사이의 선택은 비용 / 복잡도 절충이므로 사용자가 **반드시** 결정한다. RESILIENCY-02 의 답이 D (Active/Active) 또는 C (리전 간 범위의 Warm Standby) 였다면 멀티 리전이 전제되므로 사용자에게 확인한다. 그 외에는 다음을 질문한다:

```markdown
## Question: 리전 구성 (Regional Topology)
이 워크로드에 멀티 리전 배포가 필요합니까, 아니면 멀티 존 이중화를 갖춘 단일 리전으로 충분합니까?

A) 단일 리전, 멀티 존 — 존 장애는 견디지만 리전 전체 장애는 견디지 못함. 비용 낮음. (RTO/RPO 선택지 A/B/E 와 대응.)

B) 멀티 리전 active-passive — failover 로 리전 장애를 견딤. 비용 높음. (리전 간 Warm Standby / Pilot Light 와 대응.)

C) 멀티 리전 active-active — 중단 없이 리전 장애를 견딤. 최고 비용. (Active/Active 와 대응.)

X) Other (describe after [Answer]: tag below)

[Answer]: 
```

**검증**:
- 컴퓨팅 자원이 2개 이상 가용 영역에 배포되어 있다 (또는 본래 멀티 존인 서버리스 서비스 사용)
- 데이터 저장소가 멀티 존 구성을 사용한다
- 부하 분산이 여러 존에 트래픽을 분산한다
- 멀티 리전 구성이 사용자에 의해 명시적으로 선택되었고, RESILIENCY-02 의 RTO/RPO 목표와 일치한다
- 아키텍처 문서가 정적 안정성 (존 failover 에 컨트롤 플레인 의존 없음) 을 확인한다

## Rule RESILIENCY-09: 자동 확장 및 용량 관리

**규칙**: 운영 워크로드는 부하 변동에 대응하고 용량 부족으로 인한 장애를 막기 위해 자동 확장 (auto-scaling) 을 **반드시** 구현한다:
- **자동 확장 정책**: 컴퓨팅 자원은 적절한 확장 조건 (CPU, 메모리, 요청 수, 사용자 정의 지표) 으로 자동 확장을 **반드시** 구성한다
- **확장 한도**: 용량 부족과 무한 확장을 모두 막기 위해 최소 · 최대 용량 한도를 **반드시** 정의한다
- **사전 준비 (pre-warming)**: 트래픽 패턴을 예측할 수 있는 워크로드는 예약 확장 또는 사전 준비를 구성하는 것을 권장한다 (SHOULD)
- **서버리스 한도**: 서버리스 함수는 하류 서비스 과부하를 막기 위해 동시 실행 한도를 **반드시** 구성한다
- **서비스 할당량 (quota) 파악**: 팀은 워크로드와 관련된 클라우드 제공자 서비스 할당량과 한도 (예: 함수 동시 실행 수, API 요청 속도, 스토리지 요청 한도) 를 **반드시** 파악하고, 운영 개시 전에 증설이 필요한 할당량을 문서화한다. 할당량 사용률은 모니터링하고 80% 임계값에서 경보를 울리는 것을 권장한다 (SHOULD).

**검증**:
- 컴퓨팅 자원에 자동 확장이 구성되어 있다 (또는 서버리스 사용)
- 최소 · 최대 확장 한도가 정의되어 있다
- 확장 조건이 워크로드 패턴에 적절하다
- 해당되는 경우 서버리스 동시 실행 한도가 구성되어 있다
- 관련 클라우드 제공자 서비스 할당량이 파악 · 문서화되어 있다
- 예상 부하에서 초과될 수 있는 한도에 대해 할당량 증설 요청이 계획되어 있다

## Rule RESILIENCY-10: 의존 대상 격리 및 회로 차단 (Circuit Breaking)

**규칙**: 애플리케이션은 의존 대상 장애가 연쇄 장애로 번지지 않도록 하는 패턴을 **반드시** 구현한다:
- **타임아웃**: 모든 외부 호출 (HTTP, 데이터베이스, 캐시) 에 명시적 타임아웃을 **반드시** 구성한다 — 무제한 대기 금지
- **Circuit breaker**: 외부 의존 대상을 호출하는 서비스는 의존 대상이 비정상일 때 빠르게 실패하도록 circuit breaker 패턴을 구현하는 것을 권장한다 (SHOULD)
- **Bulkhead**: 핵심 워크로드는 실패한 의존 대상 하나가 공유 자원을 고갈시키지 않도록 의존 대상별 풀 (연결 풀, 스레드 풀) 을 격리하는 것을 권장한다 (SHOULD)
- **우아한 기능 저하 (graceful degradation)**: 애플리케이션은 핵심이 아닌 의존 대상을 쓸 수 없을 때의 저하 모드 동작을 **반드시** 정의한다

**검증**:
- 모든 외부 호출에 명시적 타임아웃이 구성되어 있다
- 핵심 외부 의존 대상에 circuit breaker 패턴이 구현되어 있다 (또는 해당 없음으로 문서화)
- 핵심이 아닌 의존 대상 장애 시의 기능 저하 동작이 문서화되어 있다
- 자원 고갈을 막도록 연결 풀과 자원 한도가 구성되어 있다

## Rule RESILIENCY-11: DR 전략 선택

**규칙**: 영구 상태를 가진 모든 운영 워크로드는 RTO/RPO 목표에 맞는 재해 복구 전략을 **반드시** 문서화한다:
- **전략 선택**: 비즈니스 요구사항에 따라 검증된 DR 전략 중에서 선택한다:
  - Backup & Restore (RTO/RPO: 수 시간) — 최저 비용
  - Pilot Light (RTO/RPO: 수십 분) — 데이터 실시간 유지, 서비스 대기
  - Warm Standby (RTO/RPO: 수 분) — 데이터 실시간 유지, 서비스 축소 용량 운영
  - Hot Standby / Active-Passive (RTO/RPO: 수 분) — 데이터 실시간 유지, 서비스 준비 완료
  - Active/Active (RTO/RPO: 실시간) — 최고 비용, 무중단
- **비용 정합성**: DR 전략 비용은 중단 시 비즈니스 영향으로 **반드시** 정당화한다
- **문서화**: 선택한 DR 전략은 명확한 failover 및 failback 절차와 함께 **반드시** 문서화한다

**검증**:
- 핵심 워크로드마다 DR 전략이 선택 · 문서화되어 있다
- 전략이 정의된 RTO/RPO 목표 (RESILIENCY-02) 와 맞는다
- failover 및 failback 절차가 문서화되어 있다
- DR 전략 비용이 비즈니스 영향 대비 정당화되어 있다

---

## Rule RESILIENCY-12: 데이터 백업 및 복제

**규칙**: 모든 영구 데이터는 정의된 RPO 에 따라 **반드시** 백업 및/또는 복제한다:
- **자동 백업**: 데이터베이스와 스토리지 백업은 관리형 백업 서비스 또는 예약 작업으로 **반드시** 자동화한다 (예: 자동 데이터베이스 스냅샷, 객체 스토리지 버전 관리, 또는 그에 준하는 방식)
- **리전 간 복제**: 핵심 데이터는 리전 단위 재해에 대비해 보조 리전으로 복제하는 것을 권장한다 (SHOULD)
- **백업 검증**: 백업 무결성은 테스트 복원으로 **반드시** 주기적으로 검증한다
- **보존 정책**: 백업 보존 기간은 비즈니스 및 규정 준수 요구사항에 맞춰 **반드시** 정의한다
- **암호화**: 백업은 저장 시 (at rest) **반드시** 암호화한다

**검증**:
- 모든 영구 데이터 저장소에 자동 백업이 구성되어 있다
- 핵심 데이터에 리전 간 복제가 구성되어 있다 (또는 불필요하다는 근거와 함께 문서화)
- 백업 보존 정책이 정의되어 있다
- 백업 암호화가 활성화되어 있다
- 백업 검증 절차가 문서화되어 있다 (수동이라도)

---

## Rule RESILIENCY-13: Failover 및 복구 절차

**규칙**: 모든 DR 전략은 문서화되고 테스트된 failover 및 복구 절차를 **반드시** 갖춘다:
- **런북 (runbook)**: 단계별 failover 및 failback 런북을 **반드시** 문서화한다
- **자동화**: failover 절차는 가능한 한 자동화하는 것을 권장한다 (SHOULD) (예: DNS 상태 점검 기반 라우팅, 관리형 데이터베이스 전역 복제, 전용 재해 복구 서비스)
- **소통 계획**: DR 상황에서 이해관계자와의 소통 계획을 **반드시** 정의한다
- **복구 검증**: DR 환경에서 워크로드가 올바르게 동작하는지 확인하는 failover 후 검증 단계를 **반드시** 문서화한다

**검증**:
- 단계별 절차가 담긴 failover 런북이 있다
- failback 절차가 문서화되어 있다
- 해당되는 경우 자동 failover 방식이 구성되어 있다
- failover 후 검증 단계가 정의되어 있다

## Rule RESILIENCY-14: 카오스 엔지니어링 및 DR 테스트

**규칙**: 복원력 방식은 정의된 테스트 방법을 **반드시** 갖춘다. 조직에 이미 DR 테스트나 카오스 엔지니어링 관행이 있으면, 이 규칙은 프로젝트가 새로 만들지 않고 기존 관행을 참조하도록 한다.

**확인 질문 (NFR Design 중에 질문, 가정하지 않음)**:

```markdown
## Question: 복원력 테스트 방식 (Resiliency Testing Approach)
복원력 방식 (failover, 복구) 은 어떻게 검증합니까?

A) 기존 DR 테스트 / game day / 카오스 엔지니어링 관행 사용 — 참조 자료를 알려 주십시오. AI-DLC 가 그에 맞는 테스트 시나리오를 문서화합니다.

B) 관행 없음 — AI-DLC 가 도입할 DR 테스트 일정과 카오스 실험 계획을 제안.

C) Operations phase 로 미룸 — 테스트 시나리오는 지금 정리하고, 실행은 Operations 에서.

X) Other (describe after [Answer]: tag below)

[Answer]: 
```

**검증**:
- 복원력 테스트 방식이 식별되어 있다 (사용자 답에 따라 기존 관행, 제안 계획, 또는 Operations 로 미룸)
- 선택된 DR 전략 (RESILIENCY-11) 에 대한 DR 테스트 시나리오가 문서화되어 있다
- 테스트 결과 추적 방식이 식별되어 있다 (기존 또는 제안)

**참고**: 카오스 실험과 DR 훈련의 실행은 Operations phase 활동이다. 이 규칙은 Operations 가 정해진 출발점을 갖도록, 설계 시점에 테스트 시나리오와 일정을 정리해 두게 한다.

## Rule RESILIENCY-15: 장애 대응 및 오류 교정 (Correction of Errors)

**규칙**: 모든 프로젝트는 장애 대응 프로세스와 **반드시** 연동한다. 변경 관리와 마찬가지로, 기본 전제는 조직에 이미 장애 대응 프로세스가 **있다**는 것이다 — 이 규칙은 프로젝트가 그 프로세스를 참조하고 그에 맞추도록 한다.

**확인 질문 (Requirements 또는 NFR Design 중에 질문, 가정하지 않음)**:

```markdown
## Question: 장애 대응 프로세스 (Incident Response Process)
이 워크로드의 운영 장애는 어떻게 처리합니까?

A) 기존 장애 대응 프로세스 사용 — 참조 자료를 알려 주십시오 (예: PagerDuty 런북, 사내 IR / 당직 (on-call) 프로세스). AI-DLC 가 경보와 런북을 그에 맞춥니다.

B) 정식 프로세스 없음 — AI-DLC 가 도입할 가벼운 장애 대응 및 오류 교정 (Correction of Errors, COE) 프로세스를 제안.

X) Other (describe after [Answer]: tag below)

[Answer]: 
```

**검증**:
- 장애 대응 프로세스가 이름으로 식별되어 있거나 (기존), 사용자 답에 따라 제안되어 있다
- COE / 사후 분석 (post-mortem) 방식이 식별되어 있다 (기존 조직 관행 또는 제안)
- RESILIENCY-05 의 경보가 식별된 장애 대응 프로세스로 전달된다
- 개선 조치 추적 방식이 식별되어 있다

**참고**: 사용자가 A 를 선택하면, 모델은 기존 프로세스를 **반드시** 참조하고 관측 가능성 / 경보가 그와 연동되도록 한다 — 다시 정의해서는 안 된다.

## 적용 연계 (Enforcement Integration)

이 규칙은 모든 AI-DLC stage 에 적용되는 공통 제약이다. 각 stage 에서:
- 만들어진 산출물에 대해 모든 RESILIENCY 규칙의 검증 기준을 평가한다
- stage 완료 요약에 "복원력 준수 (Resiliency Compliance)" 절을 넣어 각 규칙을 준수, 미준수, N/A 로 나열한다
- 미준수 규칙이 하나라도 있으면 차단 복원력 발견 사항이다 — 개요에 정의된 차단 발견 사항 처리를 따른다
- 설계 문서, 인프라 템플릿, 테스트 지침에 복원력 규칙 참조를 넣는다
