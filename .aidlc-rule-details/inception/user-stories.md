# User Stories - 상세 단계

## 목적 (Purpose)
**요구사항을 인수 조건을 갖춘 사용자 중심 스토리로 변환한다**

User Stories 의 초점:
- 비즈니스 요구사항을 사용자 중심 서술로 옮기기
- 각 스토리마다 명확한 인수 조건 정의
- 서로 다른 이해관계자 유형을 대표하는 사용자 persona 작성
- 팀 간 공통 이해 형성
- 구현을 위한 테스트 가능한 명세 제공

## 선행 조건 (Prerequisites)
- Workspace Detection 이 완료되어 있어야 한다
- Requirements Analysis 권장 (있으면 요구사항을 참조할 수 있음)
- Workflow Planning 에서 User Stories stage 를 실행하도록 지정되어 있어야 한다

## 지능형 평가 지침

**USER STORIES 실행 시점**: 진행하기 전에 아래 강화된 평가를 적용한다:

### 높은 우선순위 실행 (ALWAYS Execute)
- **새 사용자 기능**: 사용자가 직접 상호작용하는 모든 새 기능
- **사용자 경험 변경**: 기존 사용자 워크플로우나 인터페이스 수정
- **다중 persona 시스템**: 여러 유형의 사용자를 대상으로 하는 애플리케이션
- **고객 대상 API**: 외부 사용자나 시스템이 사용할 서비스
- **복잡한 비즈니스 로직**: 여러 시나리오나 비즈니스 규칙이 있는 요구사항
- **팀 간 프로젝트**: 여러 팀의 공통 이해가 필요한 작업

### 중간 우선순위 실행 (복잡도 평가)
- **백엔드의 사용자 영향**: 사용자 경험에 간접적으로 영향을 주는 내부 변경
- **성능 개선**: 사용자가 체감하는 이점이 있는 개선
- **통합 작업**: 사용자 워크플로우에 영향을 주는 시스템 연결
- **데이터 변경**: 사용자 데이터, 보고서, 분석에 영향을 주는 수정
- **보안 강화**: 사용자 인증이나 권한에 영향을 주는 변경

### 복잡도 평가 요소
중간 우선순위의 경우, 다음 중 하나라도 해당하면 user stories 를 실행한다:
- **범위**: 변경이 여러 컴포넌트나 사용자 접점에 걸침
- **모호성**: 요구사항에 스토리로 명확히 할 수 있는 불분명한 부분이 있음
- **위험**: 비즈니스 영향이 크거나 오해 가능성이 있음
- **이해관계자**: 요구사항에 여러 비즈니스 이해관계자가 관여
- **테스트**: 사용자 인수 테스트가 필요함
- **선택지**: 유효한 구현 방식이 여러 개 존재

### 단순한 경우에만 건너뜀
- **순수 리팩터링**: 사용자 영향이 전혀 없는 내부 코드 개선
- **격리된 버그 수정**: 범위가 명확하고 잘 정의된 단순 수정
- **인프라 전용**: 사용자에게 보이는 효과가 없는 변경
- **개발자 도구**: 빌드 프로세스, CI/CD, 개발 환경 변경
- **문서**: 기능에 영향을 주지 않는 업데이트

### 기본 결정 규칙
**확신이 없으면 user stories 를 포함하고, 명확화 질문을 한다.** 적절한 명확화를 거쳐 포괄적인 스토리를 만드는 부담보다 대개 다음 이점이 더 크다:
- 더 명확한 요구사항 이해
- 더 나은 팀 정렬
- 개선된 테스트 기준
- 향상된 이해관계자 소통
- 구현 위험 감소
- 개발 중 비용이 큰 변경 감소
- 더 나은 사용자 경험 결과

# PART 1: PLANNING

## Step 1: User Stories 필요성 검증 (MANDATORY)

**CRITICAL (필수)**: user stories 를 진행하기 전에 다음 평가를 수행한다:

### 평가 절차
1. **요청 맥락 분석**:
   - 원래 사용자 요청과 요구사항을 검토한다
   - 사용자에게 보이는 변경과 내부 전용 변경을 구분한다
   - 작업의 복잡도와 범위를 평가한다
   - 비즈니스 이해관계자의 관여 정도를 평가한다

2. **평가 기준 적용**:
   - 높은 우선순위 지표 (항상 실행) 와 대조한다
   - 중간 우선순위 요소 (복잡도 기반 결정) 를 평가한다
   - 건너뛰어야 할 단순한 경우가 아닌지 확인한다

3. **평가 결정 문서화**:
   - `aidlc-docs/inception/plans/user-stories-assessment.md` 를 작성한다
   - 이 요청에서 user stories 가 가치 있는 이유를 포함한다
   - 해당하는 구체적 평가 기준을 언급한다
   - 기대 이점 (명확성, 테스트, 이해관계자 정렬) 을 설명한다

4. **타당할 때만 진행**:
   - User stories 가 프로젝트에 분명한 가치를 더해야 한다
   - 평가에서 구체적 이점이 부담보다 크다는 것이 드러나야 한다
   - 결정은 프로젝트 이해관계자에게 설명 가능해야 한다

### 평가 문서 템플릿
```markdown
# User Stories 평가 (User Stories Assessment)

## 요청 분석
- **원래 요청**: [간단한 요약]
- **사용자 영향**: [Direct/Indirect/None]
- **복잡도 수준**: [Simple/Medium/Complex]
- **이해관계자**: [관련 당사자 목록]

## 충족한 평가 기준
- [ ] 높은 우선순위: [해당 기준 목록]
- [ ] 중간 우선순위: [복잡도 근거와 함께 해당 기준 목록]
- [ ] 이점: [user stories 로 기대하는 가치]

## 결정
**User Stories 실행**: [Yes/No]
**근거**: [상세한 정당화]

## 기대 결과
- [user stories 가 제공할 구체적 이점 목록]
- [스토리가 프로젝트 성공을 어떻게 높이는지]
```

## Step 2: 스토리 계획 작성
- 제품 책임자 (product owner) 역할을 맡는다
- 스토리 개발을 위한 단계별 실행 체크리스트가 담긴 포괄적 계획을 작성한다
- 각 단계와 하위 단계에는 체크박스 [] 가 있어야 한다
- 요구사항을 user stories 로 변환하는 방법론과 접근 방식에 집중한다

## Step 3: 맥락에 맞는 질문 생성
**지시 (DIRECTIVE)**: 요구사항과 맥락을 철저히 분석하여, 명확화가 스토리 품질과 팀 이해를 높일 모든 영역을 찾는다. 포괄적인 user story 개발을 위해 적극적으로 질문한다.

**CRITICAL (필수)**: 스토리 품질에 영향을 줄 수 있는 모호함이나 누락된 세부사항이 조금이라도 있으면 기본적으로 질문한다. 불완전하거나 불명확한 스토리를 만드는 것보다 질문을 너무 많이 하는 편이 낫다.

**질문 형식 규칙은 `common/question-format-guide.md` 참조**

- [Answer]: 태그 형식으로 질문을 문서에 넣는다
- 모든 모호함, 누락된 정보, 명확화가 필요한 영역에 집중한다
- 사용자 입력이 스토리 작성 결정을 개선할 수 있는 곳이면 어디든 질문을 생성한다
- **확신이 없으면 질문한다** - 과신은 부실한 스토리로 이어진다

**평가할 질문 범주** (모든 범주를 고려):
- **User Personas** - 사용자 유형, 역할, 특성, 동기에 대해 질문
- **스토리 세분화 수준** - 적절한 상세 수준, 스토리 크기, 분할 방식에 대해 질문
- **스토리 형식** - 형식 선호, 템플릿 사용, 문서화 기준에 대해 질문
- **분할 방식** - 구성 방법, 우선순위, 그룹화 전략에 대해 질문
- **인수 조건** - 상세 수준, 형식, 테스트 방식, 검증 방법에 대해 질문
- **사용자 여정** - 사용자 워크플로우, 상호작용 패턴, 경험 흐름에 대해 질문
- **비즈니스 맥락** - 비즈니스 목표, 성공 지표, 이해관계자 요구에 대해 질문
- **기술 제약** - 기술적 한계, 통합 요구사항, 시스템 경계에 대해 질문

## Step 4: 필수 스토리 산출물을 계획에 포함
- 스토리 계획에 다음 필수 산출물을 **항상 (ALWAYS)** 포함한다:
  - [ ] INVEST 기준을 따르는 user stories 로 stories.md 생성
  - [ ] 사용자 원형과 특성으로 personas.md 생성
  - [ ] 스토리가 Independent, Negotiable, Valuable, Estimable, Small, Testable 한지 확인
  - [ ] 각 스토리에 인수 조건 포함
  - [ ] persona 를 관련 user stories 에 매핑

## Step 5: 스토리 선택지 제시
- 계획 문서에 스토리 분할의 여러 접근 방식을 포함한다:
  - **사용자 여정 기반 (User Journey-Based)**: 스토리가 사용자 워크플로우와 상호작용을 따름
  - **기능 기반 (Feature-Based)**: 스토리를 시스템 기능과 역량 중심으로 구성
  - **Persona 기반 (Persona-Based)**: 스토리를 사용자 유형과 그 요구별로 그룹화
  - **도메인 기반 (Domain-Based)**: 스토리를 비즈니스 도메인이나 맥락 중심으로 구성
  - **Epic 기반 (Epic-Based)**: 스토리를 하위 스토리를 가진 계층형 epic 으로 구조화
- 각 접근 방식의 장단점과 이점을 설명한다
- 명확한 결정 기준이 있는 혼합 방식도 허용한다

## Step 6: 스토리 계획 저장
- 질문이 포함된 완성된 스토리 계획을 `aidlc-docs/inception/plans/` 디렉터리에 저장한다
- 파일 이름: `story-generation-plan.md`
- 사용자 입력을 위한 모든 [Answer]: 태그를 포함한다
- 계획이 포괄적이며 스토리 개발의 모든 측면을 다루는지 확인한다

## Step 7: 사용자 입력 요청
- 사용자에게 스토리 계획 문서 안의 모든 [Answer]: 태그를 직접 채우도록 요청한다
- 감사 추적과 결정 문서화의 중요성을 강조한다
- [Answer]: 태그 작성 방법을 명확히 안내한다
- 진행하기 전에 모든 질문에 답해야 함을 설명한다

## Step 8: 답변 수집
- 사용자가 문서의 [Answer]: 태그로 모든 질문에 답할 때까지 기다린다
- 모든 [Answer]: 태그가 채워질 때까지 진행하지 않는다
- 문서를 검토하여 비어 있는 [Answer]: 태그가 없는지 확인한다

## Step 9: 답변 분석 (MANDATORY)
진행하기 전에 모든 사용자 답변을 다음 관점에서 **반드시** 꼼꼼히 검토한다:
- **모호하거나 애매한 응답**: "섞어서 (mix of)", "그 중간쯤 (somewhere between)", "잘 모르겠음 (not sure)", "상황에 따라 (depends)", "아마도 (maybe)", "아마 (probably)"
- **정의되지 않은 기준이나 용어**: 명확한 정의 없이 개념을 언급
- **모순된 답변**: 서로 충돌하는 응답
- **생성 세부사항 누락**: 구현에 필요한 구체적 지침이 없는 답변
- **선택지를 합친 답변**: 명확한 결정 규칙 없이 서로 다른 방식을 합친 응답
- **불완전한 설명**: 외부 요인을 정의 없이 언급하는 답변
- **가정 기반 응답**: 명시되지 않은 지식을 전제한 답변

## Step 10: 후속 질문 (MANDATORY)
step 9 의 분석에서 모호한 답변이 하나라도 드러나면 **반드시** 다음을 수행한다:
- [Answer]: 태그를 사용한 별도의 명확화 질문 파일을 작성한다
- 모든 모호함이 완전히 해소될 때까지 승인 단계로 진행하지 않는다
- **CRITICAL (필수)**: 철저하게 - 불명확한 모든 응답에 후속 질문을 한다
- 필요한 후속 질문 예시:
  - "'A 와 B 를 섞어서' 라고 하셨는데, A 와 B 중 무엇을 쓸지 정하는 구체적 기준은 무엇인가요?"
  - "'A 와 B 의 중간쯤' 이라고 하셨는데, 정확한 중간 방식을 정의해 주실 수 있나요?"
  - "'잘 모르겠음' 이라고 하셨는데, 결정에 도움이 될 추가 정보는 무엇인가요?"
  - "'복잡도에 따라' 라고 하셨는데, 복잡도 수준과 기준값을 어떻게 정의하나요?"
  - "'혼합 방식' 을 선택하셨는데, 각 방법을 언제 쓸지 구체적 규칙은 무엇인가요?"
  - "'아마 X' 라고 하셨는데, 확실히 X 이거나 확실히 X 가 아니게 만드는 요인은 무엇인가요?"
  - "'표준 관행' 을 언급하셨는데, 그 표준 관행이 무엇인지 정의해 주실 수 있나요?"

## Step 11: 구현 세부사항 피하기
- 우선순위 결정이나 개발 작업이 아니라 스토리 작성 방법론에 집중한다
- 이 단계에서는 기술적 생성을 논의하지 않는다
- 개발 일정이나 스프린트 계획 작성은 피한다
- 스토리 구조와 형식 결정에 계속 집중한다

## Step 12: 승인 요청 기록
- 승인을 요청하기 전에, 요청 문구를 타임스탬프와 함께 `aidlc-docs/audit.md` 에 기록한다
- 승인 요청 문구 전체를 포함한다
- ISO 8601 타임스탬프 형식을 사용한다

## Step 13: 계획에 대한 명시적 승인 대기
- 사용자가 스토리 접근 방식을 명시적으로 승인할 때까지 진행하지 않는다
- 승인은 명확하고 모호하지 않아야 한다
- 사용자가 변경을 요청하면 계획을 업데이트하고 승인 절차를 반복한다

## Step 14: 승인 응답 기록
- 사용자의 승인 응답을 타임스탬프와 함께 `aidlc-docs/audit.md` 에 기록한다
- 사용자 응답 원문을 그대로 포함한다
- 승인 상태를 명확히 표시한다

- [ ] 완료되지 않은 다음 단계 (첫 번째 [ ] 체크박스) 를 찾는다
- [ ] 해당 단계의 맥락과 요구사항을 불러온다

## Step 16: 현재 단계 실행
- [ ] 현재 단계에 적힌 내용을 정확히 수행한다
- [ ] 계획에 명시된 대로 스토리 산출물을 생성한다
- [ ] Planning 에서 승인된 방법론과 형식을 따른다
- [ ] 계획에 명시된 스토리 분할 방식을 사용한다

## Step 17: 진행 상황 업데이트
- [ ] 스토리 생성 계획에서 완료한 단계를 [x] 로 표시한다
- [ ] `aidlc-docs/aidlc-state.md` 의 현재 상태를 업데이트한다
- [ ] 생성한 모든 산출물을 저장한다

## Step 18: 생성 계속 또는 완료
- [ ] 남은 단계가 있으면 Step 15 로 돌아간다
- [ ] 모든 단계가 끝나면 스토리가 다음 stage 를 위한 준비가 되었는지 확인한다
- [ ] 모든 필수 산출물이 생성되었는지 확인한다

## Step 19: 승인 요청 기록
- 승인을 요청하기 전에, 요청 문구를 타임스탬프와 함께 `aidlc-docs/audit.md` 에 기록한다
- 승인 요청 문구 전체를 포함한다
- ISO 8601 타임스탬프 형식을 사용한다

## Step 20: 완료 메시지 제시
- 다음 구조로 완료 메시지를 제시한다:
     1. **완료 알림** (필수): 항상 다음으로 시작한다:

```markdown
# 📚 User Stories 완료 (User Stories Complete)
```

     2. **AI 요약** (선택): 생성된 스토리를 구조화된 글머리표로 요약한다
        - 형식: "User stories 생성 결과 [설명] 을 작성했습니다:"
        - 생성한 핵심 persona 나열 (글머리표)
        - 작성한 user stories 를 개수와 구성과 함께 나열
        - 스토리 구조와 준수 사항 (INVEST 기준, 인수 조건) 언급
        - 워크플로우 안내 문구 ("검토해 주세요", "알려주세요", "다음 phase 로 진행", "진행하기 전에") 는 넣지 않는다
        - 사실과 내용 중심으로 유지한다
     3. **형식화된 워크플로우 메시지** (필수): 항상 다음 형식 그대로 끝맺는다:

```markdown
> **📋 <u>**검토 필요 (REVIEW REQUIRED):**</u>**  
> user stories 와 persona 를 확인해 주세요: `aidlc-docs/inception/user-stories/stories.md` 와 `aidlc-docs/inception/user-stories/personas.md`



> **🚀 <u>**다음 단계 (WHAT'S NEXT?)**</u>**
>
> **다음 중 선택할 수 있습니다:**
>
> 🔧 **변경 요청 (Request Changes)** -  검토 결과에 따라 스토리나 persona 수정 요청  
> ✅ **승인 후 계속 (Approve & Continue)** - user stories 를 승인하고 **Workflow Planning** 으로 진행

---
```

## Step 21: 생성된 스토리에 대한 명시적 승인 대기
- 사용자가 생성된 스토리를 명시적으로 승인할 때까지 진행하지 않는다
- 승인은 명확하고 모호하지 않아야 한다
- 사용자가 변경을 요청하면 스토리를 업데이트하고 승인 절차를 반복한다

## Step 22: 승인 응답 기록
- 사용자의 승인 응답을 타임스탬프와 함께 `aidlc-docs/audit.md` 에 기록한다
- 사용자 응답 원문을 그대로 포함한다
- 승인 상태를 명확히 표시한다

## Step 23: 진행 상황 업데이트
- `aidlc-state.md` 에서 User Stories stage 를 완료로 표시한다
- "Current Status" 섹션을 업데이트한다
- 다음 stage 로의 전환을 준비한다

# CRITICAL RULES (핵심 규칙)

## Planning Phase 규칙
- **맥락에 맞는 질문 (CONTEXT-APPROPRIATE QUESTIONS)**: 이 특정 맥락과 관련된 질문만 한다
- **답변 분석 필수 (MANDATORY ANSWER ANALYSIS)**: 진행하기 전에 항상 답변의 모호함을 분석한다
- **모호한 채 진행 금지 (NO PROCEEDING WITH AMBIGUITY)**: 생성 전에 모든 모호한 답변을 해소해야 한다
- **명시적 승인 필요 (EXPLICIT APPROVAL REQUIRED)**: 생성 시작 전에 사용자가 계획을 승인해야 한다

## Generation Phase 규칙
- **하드코딩된 로직 금지 (NO HARDCODED LOGIC)**: 스토리 생성 계획에 적힌 것만 실행한다
- **계획을 정확히 따름 (FOLLOW PLAN EXACTLY)**: 단계 순서에서 벗어나지 않는다
- **체크박스 업데이트 (UPDATE CHECKBOXES)**: 각 단계를 마치는 즉시 [x] 로 표시한다
- **승인된 방법론 사용 (USE APPROVED METHODOLOGY)**: Planning 에서 정한 스토리 접근 방식을 따른다
- **완료 확인 (VERIFY COMPLETION)**: 진행하기 전에 모든 스토리 산출물이 완성되었는지 확인한다

## 완료 기준 (Completion Criteria)
- 모든 계획 질문에 답했고 모호함이 해소됨
- 사용자가 스토리 계획을 명시적으로 승인함
- 스토리 생성 계획의 모든 단계가 [x] 로 표시됨
- 계획에 따라 모든 스토리 산출물 (stories.md, personas.md) 이 생성됨
- 사용자가 생성된 스토리를 명시적으로 승인함
- 스토리가 검증되어 다음 stage 를 위한 준비가 됨
