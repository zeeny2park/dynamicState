# 적응형 깊이 (Adaptive Depth)

**목적**: AI-DLC 가 문제 복잡도에 맞춰 상세 수준을 조정하는 방식 설명

## 핵심 원칙

**stage 가 실행되면 그 stage 에 정의된 모든 산출물을 만든다. "깊이" 는 그 산출물 안의 상세 수준과 엄밀성을 뜻하며, 문제의 복잡도에 맞춰 조정된다.**

## Stage 선택 vs 상세 수준

### Stage 선택 (이분법)
- **Workflow Planning** 이 각 stage 마다 결정: EXECUTE 또는 SKIP
- **EXECUTE 이면**: stage 를 실행하고 정의된 모든 산출물을 만든다
- **SKIP 이면**: stage 를 전혀 실행하지 않는다

### 상세 수준 (적응형)
- **단순한 문제**: 핵심만 담은 간결한 산출물
- **복잡한 문제**: 폭넓은 내용을 담은 포괄적인 산출물
- **모델이 결정**: 정해진 규칙이 아니라 문제의 특성에 따라

## 상세 수준에 영향을 주는 요인

모델은 적절한 상세 수준을 정할 때 다음 요인을 고려한다:

1. **요청 명확성**: 사용자의 요청이 얼마나 명확하고 완전한가?
2. **문제 복잡도**: 해결 공간이 얼마나 복잡한가?
3. **범위**: 파일 하나, 컴포넌트 하나, 여러 컴포넌트, 또는 시스템 전체?
4. **위험 수준**: 오류나 누락이 미치는 영향은?
5. **사용 가능한 맥락**: greenfield (신규) vs brownfield (기존 코드), 기존 문서
6. **사용자 선호**: 사용자가 간결함이나 상세함을 선호한다고 밝혔는가?

## 예: Requirements Analysis 산출물

**모든 시나리오에서 같은 산출물을 만든다**:
- `requirement-verification-questions.md` (필요한 경우)
- `requirements.md`

**참고**: 사용자의 최초 요청은 `audit.md` 에 기록된다 (별도의 user-intent.md 불필요)

**상세 수준은 복잡도에 따라 달라진다**:

### 단순 시나리오 (버그 수정)
- **requirement-verification-questions.md**: 필요한 명확화 질문
- **requirements.md**: 간결한 기능 요구사항, 최소한의 섹션

### 복잡 시나리오 (시스템 이전)
- **requirement-verification-questions.md**: 여러 차례, 10개 이상의 질문
- **requirements.md**: 포괄적인 기능 + 비기능 요구사항, 추적성, 인수 조건

## 예: Application Design 산출물

**모든 시나리오에서 같은 산출물을 만든다**:
- `application-design.md`
- `component-diagram.md`

**상세 수준은 복잡도에 따라 달라진다**:

### 단순 시나리오 (단일 컴포넌트)
- **application-design.md**: 기본 컴포넌트 설명, 주요 메서드
- **component-diagram.md**: 핵심 관계만 담은 단순한 도식

### 복잡 시나리오 (다중 컴포넌트 시스템)
- **application-design.md**: 상세한 컴포넌트 책임, 시그니처를 포함한 모든 메서드, 설계 패턴, 검토한 대안
- **component-diagram.md**: 모든 관계, 데이터 흐름, 연동 지점을 담은 포괄적인 도식

## 모델을 위한 지침 원칙

**"당면한 문제에 꼭 필요한 만큼만 상세하게 만든다 - 더도 말고 덜도 말고."**

- 단순한 문제를 불필요한 내용으로 인위적으로 부풀리지 않는다
- 꼭 필요한 내용을 빠뜨려 복잡한 문제를 소홀히 다루지 않는다
- 문제의 특성이 자연스럽게 상세 수준을 이끌도록 한다
- stage 가 실행되면 필요한 산출물은 항상 모두 만든다
