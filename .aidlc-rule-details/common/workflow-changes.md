# 워크플로 도중 변경과 Stage 관리 (Mid-Workflow Changes and Stage Management)

## 개요

사용자는 워크플로 진행 중에 실행 계획이나 stage 실행의 변경을 요청할 수 있다. 이 문서는 그런 요청을 안전하고 효과적으로 처리하는 지침을 제공한다.

---

## 워크플로 도중 변경의 유형

### 1. 건너뛴 Stage 추가

**상황**: 사용자가 원래 건너뛴 stage 를 추가하길 원함

**예**: "그 stage 를 건너뛰긴 했지만, 역시 user story 를 추가하고 싶어요"

**처리**:
1. **요청 확인**: "User Stories stage 를 추가하시려는 거군요. user story 와 persona 가 만들어집니다. 진행할까요?"
2. **의존 관계 점검**: 선행 stage 가 모두 완료되었는지 확인한다
3. **실행 계획 갱신**: 근거와 함께 `execution-plan.md` 에 stage 를 추가한다
4. **상태 갱신**: `aidlc-state.md` 에 stage 를 "PENDING" 으로 표시한다
5. **Stage 실행**: 일반적인 stage 실행 절차를 따른다
6. **변경 기록**: 타임스탬프와 이유를 `audit.md` 에 기록한다

**고려 사항**:
- 새 산출물의 도움을 받을 수 있는 이후 stage 를 갱신해야 할 수 있음
- 새 정보를 반영하려면 기존 산출물을 고쳐야 할 수 있음
- 일정이 늘어남

---

### 2. 계획된 Stage 건너뛰기

**상황**: 사용자가 실행하기로 계획된 stage 를 건너뛰길 원함

**예**: "NFR Design stage 는 일단 건너뛰죠"

**처리**:
1. **요청 확인**: "NFR Design 을 건너뛰시려는 거군요. NFR 패턴이나 논리 컴포넌트가 반영되지 않습니다. 진행할까요?"
2. **영향 경고**: 무엇이 빠지고 어떤 결과가 생길 수 있는지 설명한다
3. **명시적 확인 받기**: 사용자가 영향을 이해했음을 **반드시** 명시적으로 확인해야 한다
4. **실행 계획 갱신**: 이유와 함께 stage 를 "SKIPPED" 로 표시한다
5. **상태 갱신**: `aidlc-state.md` 에 stage 를 "SKIPPED" 로 표시한다
6. **이후 stage 조정**: 이후 stage 에 수동 설정이 필요할 수 있음을 기록한다
7. **변경 기록**: 타임스탬프와 이유를 `audit.md` 에 기록한다

**고려 사항**:
- 이후 stage 가 실패하거나 사람의 개입이 필요할 수 있음
- 빠진 산출물에 대한 책임은 사용자가 짐
- 필요하면 나중에 다시 추가할 수 있음

---

### 3. 현재 Stage 다시 시작

**상황**: 사용자가 현재 stage 결과에 만족하지 않아 다시 하길 원함

**예**: "이 user story 들은 마음에 안 들어요. 처음부터 다시 할 수 있을까요?"

**처리**:
1. **우려 파악**: "story 의 어떤 점을 구체적으로 바꾸고 싶으신가요?"
2. **선택지 제시**:
   - **Option A**: 기존 산출물 수정 (더 빠름, 일부 작업 보존)
   - **Option B**: 완전히 다시 시작 (깨끗한 상태, 시간 더 듦)
3. **다시 시작을 고르면**:
   - 기존 산출물 보관: `{artifact}.backup.{timestamp}`
   - 계획 파일의 stage 체크박스 초기화
   - `aidlc-state.md` 에 stage 를 "IN PROGRESS" 로 표시
   - stage 완료 상태 해제
   - 처음부터 다시 실행
4. **변경 기록**: 다시 시작하는 이유와 바뀔 내용을 기록한다

**고려 사항**:
- 기존 작업은 사라짐 (단, 백업됨)
- 의존하는 stage 를 다시 해야 할 수 있음
- 일정이 늘어남

---

### 4. 이전 Stage 다시 시작

**상황**: 사용자가 이미 완료된 stage 로 돌아가 다시 하길 원함

**예**: "앞에서 정한 아키텍처 결정을 바꾸고 싶어요"

**처리**:
1. **영향 평가**: 다시 시작할 stage 에 의존하는 stage 를 모두 찾는다
2. **사용자에게 경고**: "Application Design 을 다시 시작하면 Units Generation, unit 별 설계 (모든 unit), Code Generation 을 다시 해야 합니다. 진행할까요?"
3. **명시적 확인 받기**: 사용자가 전체 영향을 **반드시** 이해해야 한다
4. **확인되면**:
   - 영향받는 산출물을 모두 보관
   - `aidlc-state.md` 에서 영향받는 stage 를 모두 초기화
   - 영향받는 모든 계획 파일의 체크박스 해제
   - 다시 시작할 stage 로 돌아감
   - 그 지점부터 다시 실행
5. **변경 기록**: 전체 영향과 다시 시작하는 이유를 기록한다

**고려 사항**:
- 상당한 재작업 필요
- 의존하는 stage 를 모두 다시 해야 함
- 일정이 크게 늘어남
- 다시 시작보다 수정이 나은지 검토

---

### 5. Stage 깊이 변경

**상황**: 사용자가 현재 또는 다음 stage 의 깊이 수준을 바꾸길 원함

**예**: "요구사항 분석을 Standard 대신 Comprehensive 로 하죠"

**처리**:
1. **요청 확인**: "Requirements Analysis 의 깊이를 Standard 에서 Comprehensive 로 바꾸시려는 거군요. 더 꼼꼼해지지만 시간이 더 걸립니다. 진행할까요?"
2. **실행 계획 갱신**: `workflow-planning.md` 의 깊이 수준을 바꾼다
3. **방식 조정**: 해당 stage 의 Comprehensive 깊이 지침을 따른다
4. **예상치 갱신**: 새 예상 일정을 사용자에게 알린다
5. **변경 기록**: 깊이 변경과 이유를 기록한다

**고려 사항**:
- 깊이를 늘리면 = 시간은 더 들지만 품질이 좋아짐
- 깊이를 줄이면 = 빠르지만 세부 사항을 놓칠 수 있음
- stage 시작 전이나 진행 중에만 바꿀 수 있고, 완료 후에는 바꿀 수 없음

---

### 6. 워크플로 일시 중지

**상황**: 사용자가 잠시 멈췄다가 나중에 재개해야 함

**예**: "오늘은 여기서 멈추고 내일 이어서 할게요"

**처리**:
1. **현재 step 마무리**: 가능하면 진행 중인 step 을 끝낸다
2. **체크박스 갱신**: 완료된 step 을 모두 [x] 로 표시한다
3. **상태 갱신**: `aidlc-state.md` 가 현재 상태를 반영하는지 확인한다
4. **중지 기록**: 중지 지점을 `audit.md` 에 기록한다
5. **재개 안내 제공**: "다시 오시면 기존 프로젝트를 감지해서 [현재 stage, 현재 step] 부터 이어 가도록 안내하겠습니다"

**재개할 때**:
1. **기존 프로젝트 감지**: `aidlc-state.md` 가 있는지 확인한다
2. **컨텍스트 불러오기**: 완료된 stage 의 산출물을 모두 읽는다
3. **상태 표시**: 현재 stage 와 다음 step 을 보여 준다
4. **선택지 제시**: 멈춘 곳부터 이어 가기 또는 이전 작업 검토
5. **재개 기록**: 재개 지점을 `audit.md` 에 기록한다

---

### 7. 아키텍처 결정 변경

**상황**: 사용자가 모놀리스에서 마이크로서비스로 (또는 반대로) 바꾸길 원함

**예**: "역시 모놀리스 대신 마이크로서비스로 가죠"

**처리**:
1. **현재 진행 상황 평가**: 워크플로가 어디까지 진행되었는지 파악한다
2. **영향 설명**: 
   - Units Generation 이전이면: 영향 최소, 결정만 갱신
   - Units Generation 이후면: Units Generation 과 unit 별 설계를 모두 다시 해야 함
   - Code Generation 이후면: 상당한 재작업 필요
3. **방식 권장**:
   - 워크플로 초반: Application Design stage 부터 다시 시작
   - 워크플로 후반: 다시 시작 대신 수정이 가능한지 검토
4. **확인 받기**: 사용자가 변경의 전체 범위를 **반드시** 이해해야 한다
5. **변경 실행**: 영향받는 stage 에 대해 다시 시작 절차를 따른다

**고려 사항**:
- 아키텍처 변경은 연쇄적인 영향을 줌
- 워크플로 초반일수록 = 바꾸기 쉬움
- 워크플로 후반일수록 = 비용 대비 이익을 따져 봄

---

### 8. Unit 추가 · 제거

**상황**: 사용자가 Units Generation 이후 unit 을 추가하거나 제거하길 원함

**예**: "Payment unit 을 Payment 와 Billing 으로 나눠야 해요"

**처리**:
1. **영향 평가**: 설계 · 코드가 완료된 unit 이 어느 것인지 파악한다
2. **결과 설명**:
   - unit 추가: 새 unit 의 설계와 코드를 전부 해야 함
   - unit 제거: 그 기능을 다른 unit 에 다시 나눠야 함
   - unit 분할: 나뉜 두 unit 모두 설계와 코드를 다시 해야 함
3. **Unit 산출물 갱신**:
   - `unit-of-work.md` 수정
   - `unit-of-work-dependency.md` 갱신
   - `unit-of-work-story-map.md` 수정
4. **영향받는 unit 초기화**: 영향받는 unit 을 재설계 필요로 표시한다
5. **변경 실행**: 영향받는 unit 에 대해 일반적인 unit 설계 · 코드 절차를 따른다

**고려 사항**:
- 해당 unit 의 모든 후속 stage 에 영향을 줌
- 의존 관계가 바뀌면 다른 unit 에도 영향을 줄 수 있음
- 일정 영향은 영향받는 unit 수에 따라 다름

## 변경 처리 일반 지침

### 변경 전

1. **요청 이해**: 무엇을 왜 바꾸려는지 확인 질문을 한다
2. **영향 평가**: 영향받는 stage, 산출물, 의존 관계를 모두 찾는다
3. **결과 설명**: 무엇을 다시 해야 하고 일정에 어떤 영향이 있는지 명확히 알린다
4. **대안 제시**: 다시 시작보다 수정이 나을 때도 있다
5. **명시적 확인 받기**: 사용자가 영향을 **반드시** 이해하고 받아들여야 한다

### 변경 중

1. **기존 작업 보관**: 되돌릴 수 없는 변경 전에는 항상 백업한다
2. **모든 추적 갱신**: `aidlc-state.md`, 계획 파일, `audit.md` 를 서로 맞게 유지한다
3. **진행 상황 공유**: 무슨 일이 진행 중인지 사용자에게 계속 알린다
4. **변경 검증**: 모든 산출물에서 변경이 일관되는지 확인한다
5. **연속성 점검**: 변경 후에도 워크플로가 매끄럽게 이어질 수 있는지 확인한다

### 변경 후

1. **일관성 확인**: 모든 산출물이 변경 내용과 맞는지 점검한다
2. **문서 갱신**: 모든 참조가 갱신되었는지 확인한다
3. **빠짐없이 기록**: 전체 변경 이력을 `audit.md` 에 기록한다
4. **사용자 확인**: 변경이 사용자의 기대에 맞는지 확인한다
5. **워크플로 재개**: 새 상태에서 일반 실행을 이어 간다

## 변경 요청 판단 흐름도 (Decision Tree)

```
사용자가 변경을 요청함
    |
    ├─ 현재 stage 인가?
    |   ├─ 예: 현재 stage 를 수정하거나 다시 시작할 수 있음
    |   └─ 아니요: 다음 질문으로
    |
    ├─ 완료된 stage 인가?
    |   ├─ 예: 의존하는 stage 에 대한 영향 평가
    |   |   ├─ 영향 낮음: 수정하고 의존 stage 갱신
    |   |   └─ 영향 높음: 그 stage 부터 다시 시작 권장
    |   └─ 아니요: 다음 질문으로
    |
    ├─ 건너뛴 stage 를 추가하는가?
    |   ├─ 예: 선행 조건 확인, 계획에 추가, 실행
    |   └─ 아니요: 다음 질문으로
    |
    ├─ 계획된 stage 를 건너뛰는가?
    |   ├─ 예: 영향 경고, 확인 받기, 건너뛰기
    |   └─ 아니요: 다음 질문으로
    |
    └─ 깊이 수준을 바꾸는가?
        ├─ 예: 계획 갱신, 방식 조정
        └─ 아니요: 사용자와 요청 내용 확인
```

## 모범 사례

1. **항상 확인**: 사용자의 명시적 확인 없이 되돌릴 수 없는 변경을 하지 않는다
2. **영향 설명**: 사용자는 결정 전에 결과를 이해해야 한다
3. **선택지 제시**: 변경을 처리하는 방법이 여러 가지일 때가 있다
4. **먼저 보관**: 되돌릴 수 없는 변경 전에는 항상 백업한다
5. **모두 갱신**: 모든 추적 파일을 서로 맞게 유지한다
6. **꼼꼼한 기록**: 감사 기록을 위해 모든 변경을 문서화한다
7. **사후 검증**: 워크플로가 매끄럽게 이어질 수 있는지 확인한다
8. **유연하게**: 워크플로는 경직된 절차를 강요하지 말고 사용자 요구에 맞춰야 한다
