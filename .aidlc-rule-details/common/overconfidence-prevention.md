# 과신 방지 가이드 (Overconfidence Prevention Guide)

## 문제 정의

AI-DLC 는 복잡한 프로젝트 의도 설명에 대해서도 명확화 질문을 충분히 하지 않는 과신을 보였다. 그 결과 제대로 요구사항을 수집하는 대신 가정을 세우게 되었다.

## 근본 원인 분석

과신 문제는 여러 stage 에서 질문을 건너뛰도록 부추기는 지시문 때문에 생겼다:

1. **Functional Design**: "해당하지 않으면 범주 전체를 건너뛴다"
2. **User Stories**: "범주는 영감을 얻는 용도로 사용하고, 필수 체크리스트로 쓰지 않는다"
3. **Requirements Analysis**: 질문을 최소화하도록 부추기는 비슷한 패턴
4. **NFR Requirements**: 철저한 분석을 막는 "~인 경우에만" 조건

이 지시문들은 포괄적인 요구사항 수집을 장려하기보다 AI 가 질문을 피하도록 만들고 있었다.

## 적용한 해결책

### 질문 생성 철학 변경

**기존 방식**: "꼭 필요한 경우에만 질문한다"
**새 방식**: "의심스러우면 질문한다 - 과신은 나쁜 결과로 이어진다"

### 주요 변경 사항

#### 1. Requirements Analysis Stage
- "필요한 경우에만" 에서 "매우 명확한 경우가 아니면 항상 질문을 만든다" 로 변경
- 포괄적인 평가 영역 추가 (기능, 비기능, 비즈니스 맥락, 기술 맥락)
- 능동적인 질문 방식 강조

#### 2. User Stories Stage
- "범주 전체를 건너뛴다" 지시문 삭제
- 평가할 포괄적인 질문 범주 추가
- 답변 분석 요구사항 강화
- 후속 질문 의무 강화

#### 3. Functional Design Stage
- "~인 경우에만" 조건을 포괄적인 평가로 대체
- 질문 범주 추가 (데이터 흐름, 연동 지점, 오류 처리)
- 모호함 탐지 · 해소 요구사항 강화

#### 4. NFR Requirements Stage
- 기본 NFR 을 넘어 질문 범주 확대
- 신뢰성, 유지보수성, 사용성 고려 사항 추가
- 기술적 모호함에 대한 답변 분석 강화

### 새 지침 원칙

1. **기본은 질문하기**: 조금이라도 모호하면 명확화 질문을 한다
2. **포괄적 범위**: 관련된 모든 범주를 평가하고, 영역을 건너뛰지 않는다
3. **철저한 분석**: 사용자의 모든 답변을 모호함이 있는지 주의 깊게 분석한다
4. **필수 후속 질문**: 불명확한 답변이 하나라도 있으면 후속 질문을 만든다
5. **모호한 채로 진행 금지**: 모든 모호함이 해소될 때까지 다음으로 넘어가지 않는다

## 적용 지침

### 질문 생성 시
- 모든 질문 범주를 평가하고, 하나도 건너뛰지 않는다
- 명확히 하면 품질이 좋아지는 곳이면 어디든 질문한다
- 각 stage 에 포괄적인 질문 범주를 포함한다
- 질문은 빼기보다 넣는 쪽을 기본으로 한다

### 답변 분석 시
- 모호한 답변을 찾는다: "depends", "maybe", "not sure", "mix of", "somewhere between" (예: "상황에 따라", "아마도", "잘 모르겠음", "섞어서", "그 중간쯤")
- 정의되지 않은 용어와 외부 개념에 대한 언급을 찾아낸다
- 서로 모순되거나 불완전한 답변을 찾아낸다
- 모호함이 하나라도 있으면 후속 질문을 만든다

### 후속 질문 시
- 모호함이 발견되면 별도의 명확화 파일을 만든다
- 각 모호함을 해소할 구체적인 질문을 한다
- 불명확한 답변이 모두 명확해질 때까지 진행하지 않는다
- 철저하게 한다 - 덜 명확히 하는 것보다 지나치게 명확히 하는 편이 낫다

## 품질 보증

### 주의할 위험 신호
- 복잡한 프로젝트에서 질문을 하나도 하지 않고 stage 가 완료됨
- 모호하거나 불분명한 사용자 답변으로 진행함
- 근거 없이 질문 범주 전체를 건너뜀
- 명확화를 요청하는 대신 가정을 세움

### 성공 지표
- 프로젝트 복잡도에 맞는 수의 명확화 질문
- 사용자 답변을 철저히 분석하고 필요하면 후속 질문
- 구현으로 넘어가기 전에 명확하고 모호하지 않은 요구사항
- 초기에 더 잘 명확히 한 덕분에 이후 stage 에서 변경 필요 감소

## 유지 관리

다음 경우에 이 가이드를 참조한다:
- AI-DLC 에 새 stage 를 추가할 때
- 기존 stage 지시문을 갱신할 때
- 과신 문제에 대해 AI-DLC 성능을 검토할 때
- 팀원에게 AI-DLC 질문 생성 원칙을 교육할 때

## 핵심 요점

**잘못된 가정을 하는 것보다 질문을 너무 많이 하는 편이 낫다.** 초기에 명확화 질문을 하는 비용은 가정에 기반해 잘못된 솔루션을 구현하는 비용보다 훨씬 적다.
