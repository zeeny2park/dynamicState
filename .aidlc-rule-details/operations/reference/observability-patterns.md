# 관측 패턴 (Observability Patterns)

지표, 로그, 추적으로 시스템 동작을 들여다볼 수 있게 해 빠른 진단과 선제적 감지를 가능하게 한다.

## 관측의 세 기둥 (The Three Pillars of Observability)

### 1. 지표 (Metrics)
시간에 따라 집계한 수치 측정값이다. 카디널리티와 비용이 낮아 알림과 대시보드에 적합하다.
- **유형**: Counter (항상 증가), Gauge (오르내림), Histogram (값의 분포).
- 업무 지표를 직접 내보낸다: 분당 주문 수, 시간당 결제 실패, 일일 가입 수.

### 2. 로그 (Logs)
개별 사건의 시간 표시 기록이다. 카디널리티와 양이 많다.
- 일관된 필드를 가진 구조화 로그 (JSON) 를 쓴다: `timestamp`, `level`, `requestId`, `service`, `message`.
- header 로 전파하는 공유 `requestId` 또는 `traceId` 로 서비스 간 로그를 연결한다.
- 서비스 · 환경별로 로그를 나눠 모은다.

### 3. 추적 (Traces)
여러 서비스를 거치는 요청의 종단 간 경로다. 지연 시간 분해와 의존 관계를 보여 준다.
- 업무 로직, 데이터베이스 쿼리, 외부 HTTP 호출 구간을 계측한다.
- 서비스 의존 관계를 시각화하고 지연 병목을 찾는다.

## 네 가지 황금 신호 (The Four Golden Signals, Google SRE)

모든 서비스에서 다음 네 신호를 감시한다.

1. **지연 시간 (Latency)**: 요청을 처리하는 시간. 백분위 (p50, p95, p99) 로 측정한다. 성공 요청과 실패 요청을 따로 추적한다.
2. **트래픽 (Traffic)**: 시스템에 걸리는 수요. API 는 초당 요청 수, 큐는 초당 메시지 수, WebSocket 은 활성 연결 수.
3. **오류 (Errors)**: 실패한 요청의 비율. 명시적 오류 (5xx) 와 암묵적 오류 (잘못된 응답, timeout, 재시도) 를 모두 포함한다.
4. **포화 (Saturation)**: 시스템이 얼마나 찼는지. CPU 사용률, 메모리 사용량, 디스크 I/O, 연결 풀 사용량.

## 대시보드 · 알람

### 대시보드 설계
- 서비스마다 대시보드 1개, 맨 위에 황금 신호를 둔다.
- 의존 대상 상태를 포함한다: 하위 서비스 지연 시간, 데이터베이스 연결, 큐 깊이.
- 파생 지표를 계산해 둔다: 오류율 = errors / (errors + successes) * 100.
- 서비스 간 일관성을 위해 대시보드 배치를 표준화한다.

### 알람 구성
- 원인이 아니라 증상에 알람을 건다. "CPU > 80%" 가 아니라 "오류율 > 1%" 에 알린다.
- 복합 알람으로 잡음을 줄인다: 여러 조건이 동시에 참일 때만 알린다.
- 적절한 평가 기간을 정한다: 일시적 급등에 울리는 단일 데이터 포인트 알람을 피한다. 안정성을 위해 `3 out of 5 datapoints` 를 쓴다.
- 알람 조치를 정한다: 담당자 알림, 자동 교정 스크립트, 장애 기록 생성.
- 심각도 등급: P1 (당번 호출), P2 (메신저 알림, 몇 시간 안에 수정), P3 (티켓, sprint 안에 수정).

## 분산 추적 (Distributed Tracing)

- 요청이 거치는 모든 구간 (API, 백그라운드 작업, 외부 호출) 에 추적을 켠다.
- 애플리케이션 로직용 사용자 정의 구간 (span) 을 만든다.
- 핵심 차원에 검색 가능한 속성을 붙인다: `customerId`, `orderStatus`, `region`.
- 디버깅 세부 정보는 검색하지 않는 부가 정보로 붙인다: 요청/응답 본문, 쿼리 매개변수.
- 조건으로 trace 를 찾는다 (예: 특정 서비스에서 응답 3초 초과).

## 로그 쿼리 패턴

운영 문제 해결에 유용한 질문이다. 쓰는 로그 도구의 문법으로 옮겨 쓴다.

| 질문 | 방법 |
| --- | --- |
| 시간대별 오류 수 | `ERROR` 로그를 5분 단위로 세기 |
| 가장 느린 요청 | 처리 시간 1000ms 초과 요청을 처리 시간 내림차순으로 20건 |
| 상태 코드별 요청 수 | 응답 상태 코드로 묶어 세기 |
| 시작 직후 지연 영향 | 프로세스 시작 직후 요청의 평균 · 최대 처리 시간을 10분 단위로 |

## 이상 감지 (Anomaly Detection)

- 과거 데이터로 기준 (baseline) 을 세우고 벗어나면 알린다.
- 패턴이 안정적인 지연 시간 · 오류율 지표에 켠다.
- 허용 가능한 변동에 맞춰 감지 대역 폭을 정한다 (표준편차 2배가 흔한 출발점이다).
- 이상 감지와 고정 임계값을 함께 쓴다: 이상 감지는 점진적 drift 를, 고정 임계값은 급성 장애를 잡는다.

## 로그 집계 · 보존 (Log Aggregation and Retention)

- 모든 로그를 일관된 이름 규칙으로 한곳에 모은다 (예: `{환경}/{서비스}`).
- 로그 묶음마다 보존 정책을 정한다: 개발 30일, staging 90일, 운영 1-3년 (또는 준수 요구사항에 따라).
- 오래된 로그는 저렴한 보관 저장소로 옮긴다 (예: 90일 초과).
- 여러 환경 · 시스템이면 로그를 한곳에서 조회할 수 있게 모은다.

## 합성 모니터링 (Synthetic Monitoring)

- 일정에 따라 (1-5분마다) 스크립트 점검을 실행한다.
- 핵심 사용자 여정을 테스트한다: 로그인, 주문, 대시보드 보기.
- 실제 사용자가 보고하기 전에 문제를 감지한다.
- 합성 점검 실패는 P1 심각도로 알린다. 사용자 경로가 고장 났다는 뜻이다.
- UI 비중이 큰 애플리케이션은 시각 모니터링 (화면 캡처 비교) 을 쓴다.
